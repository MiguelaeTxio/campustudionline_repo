1.1. Conceptos Clave de Bases de Datos

1.1.1. ¿Qué es una Base de Datos?

Una base de datos es una colección organizada de información o datos estructurados, que normalmente se almacena electrónicamente en un sistema informático. El objetivo principal de una base de datos es almacenar y recuperar información de manera eficiente, segura y consistente.

Piensa en ejemplos cotidianos:

  • La agenda de contactos de tu teléfono es una pequeña base de datos.
  • El catálogo de una biblioteca es una base de datos de libros.
  • El sistema de inventario de una tienda es una base de datos de productos.
  • Las redes sociales almacenan perfiles de usuario, publicaciones y conexiones en grandes bases de datos.

Las bases de datos permiten que múltiples usuarios accedan y modifiquen los datos simultáneamente (con los controles adecuados), y facilitan la búsqueda, el filtrado y la generación de informes a partir de la información almacenada.

[Volver al Índice Principal]

1.1.2. Sistemas Gestores de Bases de Datos (SGBD/DBMS)

Un Sistema Gestor de Bases de Datos (SGBD), o Database Management System (DBMS) en inglés, es un conjunto de programas (software) que permiten a los usuarios crear, mantener y controlar el acceso a una base de datos. Actúa como una interfaz entre la base de datos física (los archivos donde se almacenan los datos) y los usuarios o aplicaciones que necesitan acceder a esa información.

Las funciones principales de un SGBD incluyen:

  • Definición de datos: Permite definir la estructura de la base de datos, como las tablas, los tipos de datos de cada columna y las relaciones entre tablas.
  • Manipulación de datos: Permite insertar, consultar, actualizar y eliminar datos.
  • Control de concurrencia: Gestiona el acceso simultáneo de múltiples usuarios a los datos, evitando conflictos e inconsistencias.
  • Seguridad e integridad: Proporciona mecanismos para controlar quién puede acceder a los datos y qué pueden hacer, y para asegurar que los datos cumplan ciertas reglas (integridad).
  • Recuperación ante fallos: Ofrece herramientas para realizar copias de seguridad y restaurar la base de datos en caso de fallos del sistema.
  • Optimización de consultas: Intenta ejecutar las solicitudes de datos de la manera más eficiente posible.

Algunos ejemplos populares de SGBD son:

  • Relacionales (RDBMS): MySQL, PostgreSQL, Oracle Database, Microsoft SQL Server, SQLite.
  • NoSQL: MongoDB, Cassandra, Redis, Couchbase.

En este curso, nos centraremos en MySQL, que es un SGBD relacional.

1.1.3. Modelos de Bases de Datos

Un modelo de base de datos define la estructura lógica de una base de datos y determina la manera en que los datos se almacenan, organizan y manipulan. Existen varios modelos, pero el más extendido es el modelo relacional.

[Volver al Índice Principal]

1.1.3.1. Modelo Relacional

El modelo relacional, propuesto por Edgar F. Codd en 1970, es el modelo de base de datos más utilizado en la actualidad. Se basa en los principios de la teoría de conjuntos y la lógica de predicados.

Características principales del modelo relacional:

  • Estructura de Tablas: Los datos se organizan en tablas bidimensionales, también conocidas como "relaciones". Cada tabla consta de filas y columnas.
  • Filas (Tuplas o Registros): Cada fila representa una instancia única de un objeto o entidad. Por ejemplo, una fila en una tabla "Clientes" representaría un cliente específico.
  • Columnas (Atributos): Cada columna representa una propiedad o característica de la entidad. Por ejemplo, en la tabla "Clientes", las columnas podrían ser "ID_Cliente", "Nombre", "Email", "Teléfono".
  • Tipos de Datos: Cada columna tiene un tipo de dato específico (ej. número entero, cadena de texto, fecha) que define el tipo de valores que puede almacenar.
  • Claves Primarias: Cada tabla suele tener una columna (o un conjunto de columnas) designada como clave primaria, cuyo valor identifica unívocamente cada fila dentro de la tabla.
  • Claves Foráneas: Se utilizan para establecer relaciones entre tablas. Una clave foránea en una tabla apunta a la clave primaria de otra tabla, creando un vínculo entre ellas.
  • Lenguaje de Consulta (SQL): El lenguaje estándar para interactuar con bases de datos relacionales es SQL (Structured Query Language).

El modelo relacional es valorado por su simplicidad conceptual, flexibilidad y la solidez de sus fundamentos teóricos, lo que facilita la integridad y consistencia de los datos.

1.1.3.2. Otros Modelos (NoSQL, Jerárquico, Red)

Aunque el modelo relacional es dominante, existen otros modelos de bases de datos, cada uno con sus propias fortalezas y casos de uso:

  • Modelo Jerárquico: Organiza los datos en una estructura de árbol, donde cada registro padre puede tener varios registros hijos, pero cada hijo solo tiene un padre. Fue uno de los primeros modelos, utilizado en sistemas mainframe. Un ejemplo es el sistema de archivos de un ordenador.
  • Modelo de Red: Similar al jerárquico, pero permite que un registro hijo tenga múltiples padres, creando una estructura de grafo más flexible. Fue una evolución del modelo jerárquico.
  • Modelo Orientado a Objetos: Los datos se almacenan como objetos, tal como se definen en la programación orientada a objetos. Estos sistemas permiten herencia y otros conceptos de POO directamente en la base de datos.
  • Modelo NoSQL: Es una categoría amplia que engloba varios tipos de bases de datos no relacionales, diseñadas para escenarios específicos donde el modelo relacional puede no ser el más eficiente o escalable. Incluyen:
    • Documentales: Almacenan datos en documentos (ej. JSON, BSON, XML), como MongoDB. Son flexibles en cuanto al esquema.
    • Clave-Valor: Almacenan datos como pares de clave y valor, muy rápidas para búsquedas por clave, como Redis o Amazon DynamoDB.
    • Orientadas a Columnas (o Familia de Columnas): Almacenan datos por columnas en lugar de por filas, optimizadas para agregaciones y análisis sobre grandes volúmenes de datos, como Apache Cassandra o HBase.
    • Grafos: Diseñadas para almacenar y navegar relaciones complejas entre entidades, como Neo4j.
    Las bases de datos NoSQL suelen destacar por su escalabilidad horizontal, alta disponibilidad y flexibilidad de esquema.

La elección del modelo de base de datos depende de los requisitos específicos de la aplicación, como la estructura de los datos, los patrones de consulta, las necesidades de escalabilidad y la consistencia requerida.

1.1.4. Terminología Básica (Tabla, Fila, Columna, Clave Primaria, Clave Foránea)

Para trabajar con bases de datos relacionales, es fundamental comprender la siguiente terminología:

  • Entidad: Un objeto o concepto del mundo real sobre el cual queremos almacenar información. Por ejemplo: "Cliente", "Producto", "Pedido". En el modelo relacional, las entidades suelen representarse como tablas.
  • Atributo: Una propiedad o característica de una entidad. Por ejemplo, para la entidad "Cliente", los atributos podrían ser "Nombre", "Dirección", "Email". En una tabla, los atributos corresponden a las columnas.
  • Tabla (o Relación): Es la estructura fundamental donde se almacenan los datos en una base de datos relacional. Consiste en una colección de filas y columnas. Representa un conjunto de entidades del mismo tipo. 
    Ejemplo de tabla "Clientes":
+----+----------+-----------------------+
| ID | Nombre   | Email                 |
+----+----------+-----------------------+
| 1  | Ana Cruz | ana.cruz@example.com  |
| 2  | Luis Sol | luis.sol@example.com  |
+----+----------+-----------------------+
  • Fila (o Tupla / Registro): Cada entrada horizontal en una tabla. Representa una instancia específica de la entidad que la tabla describe. Por ejemplo, la fila `(1, 'Ana Cruz', 'ana.cruz@example.com')` es un registro de un cliente.
  • Columna (o Atributo / Campo): Cada entrada vertical en una tabla. Define un tipo específico de dato para todas las filas de la tabla. Por ejemplo, la columna "Nombre" contiene los nombres de todos los clientes.
  • Clave Primaria (Primary Key - PK): Es una columna (o un conjunto de columnas) cuyo valor identifica de forma única cada fila en una tabla. Las claves primarias no pueden contener valores nulos (NULL) y deben ser únicas. Por ejemplo, en la tabla "Clientes", la columna "ID" podría ser la clave primaria.
  • Clave Foránea (Foreign Key - FK): Es una columna (o un conjunto de columnas) en una tabla que establece un enlace con la clave primaria de otra tabla (o, a veces, de la misma tabla). Las claves foráneas son el mecanismo para implementar relaciones entre tablas y asegurar la integridad referencial (que los valores de la FK existan como PK en la tabla referenciada).

    Por ejemplo, si tenemos una tabla "Pedidos" con una columna "ID_Cliente", esta columna sería una clave foránea que referencia la columna "ID" de la tabla "Clientes".

  • Índice (Index): Es una estructura de datos especial asociada a una tabla que permite acelerar las operaciones de búsqueda y recuperación de datos. Las claves primarias suelen tener un índice creado automáticamente. Se pueden crear índices adicionales en otras columnas que se usen frecuentemente en condiciones de búsqueda.
  • Esquema (Schema): Es la descripción de la estructura de la base de datos. Incluye la definición de las tablas, sus columnas, los tipos de datos, las claves, los índices y las relaciones.

1.2. Introducción a MySQL

[Volver al Índice Principal]

1.2.1. ¿Qué es MySQL?

MySQL es uno de los Sistemas Gestores de Bases de Datos Relacionales (RDBMS) de código abierto más populares del mundo. Está basado en SQL (Structured Query Language), el lenguaje estándar para interactuar con bases de datos relacionales.

MySQL es conocido por su fiabilidad, rendimiento y facilidad de uso, lo que lo ha convertido en una opción muy extendida para una amplia gama de aplicaciones, desde pequeños proyectos personales y sitios web hasta grandes aplicaciones empresariales y plataformas web de alto tráfico.

Es un componente clave de la pila de software LAMP (Linux, Apache, MySQL, PHP/Perl/Python), una plataforma de desarrollo web de código abierto muy popular.

Originalmente desarrollado por la empresa sueca MySQL AB, fue adquirido por Sun Microsystems en 2008, y posteriormente Sun fue adquirida por Oracle Corporation en 2010, que es la actual propietaria y desarrolladora principal de MySQL.

[Volver al Índice Principal]

1.2.2. Historia y Características Principales

Historia Breve:

  • 1995: Primera versión interna de MySQL desarrollada por Michael "Monty" Widenius y David Axmark.
  • Años 2000: Crecimiento rápido en popularidad, especialmente en el desarrollo web.
  • 2008: MySQL AB es adquirida por Sun Microsystems.
  • 2010: Oracle Corporation adquiere Sun Microsystems, convirtiéndose en el propietario de MySQL.
  • Post-Adquisición: Oracle ha continuado el desarrollo de MySQL, ofreciendo tanto versiones comunitarias como comerciales. MariaDB, un fork de MySQL liderado por Monty Widenius, surgió como una alternativa completamente de código abierto.

Características Principales de MySQL:

  • Código Abierto: La versión MySQL Community Edition es gratuita y de código abierto bajo la licencia GPL.
  • Rendimiento: Conocido por su rapidez, especialmente para operaciones de lectura intensiva.
  • Escalabilidad: Puede manejar bases de datos de gran tamaño y un alto número de conexiones. Soporta replicación para distribuir la carga y mejorar la disponibilidad.
  • Multiplataforma: Funciona en una gran variedad de sistemas operativos, incluyendo Linux, Windows, macOS, Solaris, etc.
  • Seguridad: Ofrece un sistema de privilegios flexible para controlar el acceso a los datos, así como soporte para conexiones seguras (SSL/TLS).
  • Motores de Almacenamiento (Storage Engines): Una característica distintiva de MySQL es su arquitectura de motores de almacenamiento conectables. Esto permite elegir el motor más adecuado para diferentes tablas según las necesidades:
    • InnoDB: Es el motor por defecto en versiones recientes. Ofrece transacciones ACID, claves foráneas, y recuperación ante fallos. Optimizado para alta concurrencia y fiabilidad.
    • MyISAM: Anteriormente el motor por defecto. Es más rápido para lecturas y búsquedas de texto completo, pero no soporta transacciones ni claves foráneas de forma robusta. Menos utilizado para nuevas aplicaciones que requieren integridad transaccional.
    • Otros motores: MEMORY (para tablas en memoria), CSV, ARCHIVE, etc.
  • Replicación: Permite copiar datos de un servidor MySQL (maestro) a uno o más servidores (esclavos), útil para balanceo de carga, copias de seguridad y alta disponibilidad.
  • Soporte de Estándares SQL: Implementa una gran parte del estándar SQL, aunque con algunas extensiones y variaciones propias.
  • Amplia Comunidad y Ecosistema: Cuenta con una gran comunidad de usuarios y desarrolladores, abundante documentación, y una amplia gama de herramientas y conectores para diversos lenguajes de programación.

1.2.3. Ventajas de usar MySQL

MySQL ofrece numerosas ventajas que contribuyen a su popularidad:

  • Coste (Código Abierto): La versión Community es gratuita, lo que reduce significativamente los costes de licencia en comparación con SGBD comerciales.
  • Facilidad de Uso e Instalación: Es relativamente fácil de instalar, configurar y administrar, especialmente para aplicaciones web comunes.
  • Rendimiento: Ofrece un excelente rendimiento, especialmente para aplicaciones web y cargas de trabajo con muchas lecturas. Su arquitectura de motores de almacenamiento permite optimizar para diferentes escenarios.
  • Fiabilidad y Estabilidad: MySQL es un sistema maduro y probado en producción en millones de sitios y aplicaciones, lo que garantiza un alto grado de fiabilidad.
  • Escalabilidad: Se puede escalar verticalmente (mejorando el hardware del servidor) u horizontalmente (mediante replicación y clustering) para manejar cargas crecientes.
  • Multiplataforma: Su disponibilidad en múltiples sistemas operativos lo hace muy versátil.

  • Amplia Adopción y Ecosistema de Herramientas: Muchos servicios de hosting lo ofrecen por defecto, y hay una gran cantidad de herramientas de administración, desarrollo y conectores para casi todos los lenguajes de programación populares.

  • Flexibilidad con Motores de Almacenamiento: La capacidad de elegir diferentes motores de almacenamiento para diferentes tablas dentro de la misma base de datos ofrece una flexibilidad única para optimizar el rendimiento y las características según las necesidades específicas de cada tabla.

    • Apply Configuration: Haz clic en "Execute" para aplicar la configuración.

1.3.3. Instalación en Linux (Debian/Ubuntu y RHEL/CentOS)

En Linux, la instalación a través del gestor de paquetes de tu distribución suele ser la forma más sencilla.

Debian/Ubuntu:
  1. Actualizar lista de paquetes:

  2. Instalar MySQL Server:

    sudo mysql_secure_installation
    Este script te guiará a través de varios pasos para mejorar la seguridad:
    • Configurar el plugin VALIDATE PASSWORD (opcional).
    • Cambiar la contraseña de root (si no se estableció o quieres cambiarla).
    • Eliminar usuarios anónimos.
    • Deshabilitar el inicio de sesión remoto de root (recomendado para producción).

    • Recargar las tablas de privilegios.

    sudo systemctl status mysql

RHEL/CentOS/Fedora (usando DNF, anteriormente YUM):

En sistemas basados en RHEL, puede ser necesario habilitar primero el repositorio de MySQL si quieres una versión específica. Consulta la documentación oficial de MySQL para obtener los repositorios de MySQL Yum.

Si usas los repositorios por defecto de la distribución (que podrían tener una versión más antigua):

  1. Instalar MySQL Server (ej. MariaDB si es el fork por defecto, o mysql-community-server si tienes el repo de Oracle): 
    sudo dnf install mysql-server # O el nombre del paquete específico
    O, si has configurado el repositorio de MySQL: 
    sudo dnf install mysql-community-server
  2. Iniciar el servicio MySQL y habilitarlo para el arranque: 
    sudo systemctl start mysqld # O mysql
sudo systemctl enable mysqld # O mysql
  3. Obtener la contraseña temporal de root (si aplica): Algunas versiones la generan y la guardan en /var/log/mysqld.log. 
    sudo grep 'temporary password' /var/log/mysqld.log
  4. Asegurar la instalación: 
    sudo mysql_secure_installation
    Sigue las instrucciones, similar a Debian/Ubuntu. Si obtuviste una contraseña temporal, deberás cambiarla aquí.
  5. Verificar el estado del servicio: 
    sudo systemctl status mysqld # O mysql

Nota sobre autenticación: En versiones recientes de MySQL en algunas distribuciones de Linux, el usuario root de MySQL puede estar configurado para usar el plugin auth_socket o unix_socket. Esto significa que solo puedes iniciar sesión como root de MySQL si eres el usuario root del sistema (o usas sudo). Si deseas habilitar la autenticación por contraseña para root, necesitarás conectarte como root del sistema y alterar el usuario: 

sudo mysql
ALTER USER 'root'@'localhost' IDENTIFIED WITH mysql_native_password BY 'TuNuevaContraseña';
FLUSH PRIVILEGES;
EXIT;
Después de esto, podrás conectarte como mysql -u root -p.

1.4.1. Conexión al Servidor MySQL

Para realizar cualquier operación, primero debes conectarte al servidor MySQL.

Usando el Cliente de Línea de Comandos (mysql CLI):
  1. Abre tu terminal o símbolo del sistema.
  2. Ejecuta el comando de conexión. Lo más común es conectarse como el usuario root (el superusuario de MySQL) al servidor local: 
    mysql -u root -p
  3. El sistema te pedirá la contraseña que estableciste para el usuario root durante la instalación. Introdúcela y presiona Enter.
  4. Si la conexión es exitosa, verás un mensaje de bienvenida y el prompt mysql>.

Si necesitas conectarte con otro usuario, o a un servidor remoto, usarías:

mysql -h nombre_del_host -P puerto -u tu_usuario -p
  • -h nombre_del_host: Especifica el nombre del host o la dirección IP del servidor MySQL (si es local, puedes omitirlo o usar localhost o 127.0.0.1).
  • -P puerto: Especifica el puerto del servidor MySQL (por defecto es 3306; la 'P' es mayúscula).
  • -u tu_usuario: El nombre de usuario de MySQL.
  • -p: Indica que se proporcionará una contraseña.
Usando MySQL Workbench:
  1. Abre MySQL Workbench.
  2. En la pantalla de inicio, verás una sección para "MySQL Connections". Puedes hacer clic en el signo "+" para crear una nueva conexión o editar una existente (a menudo se crea una conexión a localhost por defecto durante la instalación).
  3. Configurar Nueva Conexión:
    • Connection Name: Un nombre descriptivo para tu conexión (ej. "Localhost Dev").
    • Connection Method: Usualmente "Standard (TCP/IP)".
    • Parameters:
      • Hostname: 127.0.0.1 o localhost para el servidor local.
      • Port: 3306 (o el puerto que hayas configurado).
      • Username: root (o el usuario que quieras usar).
      • Password: Puedes hacer clic en "Store in Vault..." o "Store in Keychain..." para guardar la contraseña (se te pedirá al conectarte si no la guardas).
  4. Haz clic en "Test Connection" para verificar que los parámetros son correctos. Si todo está bien, aparecerá un mensaje de éxito.
  5. Haz clic en "OK" para guardar la conexión.
  6. Ahora puedes hacer doble clic en la conexión guardada en la pantalla de inicio de Workbench para abrir el editor SQL y las herramientas de administración para ese servidor.

1.4.2. Comandos Básicos en el Cliente MySQL

Una vez conectado a través del cliente mysql>, aquí tienes algunos comandos básicos para empezar (recuerda que deben terminar con ;):

  • SHOW DATABASES;

    Muestra una lista de todas las bases de datos a las que tienes acceso en el servidor.

    mysql> SHOW DATABASES;
+--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| performance_schema |
| sys                |
+--------------------+
    (Verás estas bases de datos del sistema, y cualquier otra que hayas creado).
  • CREATE DATABASE nombre_de_la_base_de_datos;

    Crea una nueva base de datos. Ejemplo:

    mysql> CREATE DATABASE mi_tienda;
Query OK, 1 row affected (0.01 sec)
  • USE nombre_de_la_base_de_datos;

    Selecciona una base de datos para trabajar con ella. Cualquier comando SQL posterior se aplicará a esta base de datos. Ejemplo:

    mysql> USE mi_tienda;
Database changed
  • SHOW TABLES;

    Si has seleccionado una base de datos con USE, este comando muestra todas las tablas dentro de esa base de datos.

    mysql> SHOW TABLES;
Empty set (0.00 sec)  -- (Si la base de datos está vacía)
  • DESCRIBE nombre_de_la_tabla; (o DESC nombre_de_la_tabla;)

    Muestra la estructura de una tabla específica (nombres de columnas, tipos de datos, claves, etc.).

  • SELECT VERSION();

    Muestra la versión del servidor MySQL.

    mysql> SELECT VERSION();
+-----------+
| VERSION() |
+-----------+
| 8.0.xx    |
+-----------+
  • SELECT USER();

    Muestra el usuario actual con el que estás conectado.

  • SELECT DATABASE();

    Muestra la base de datos actualmente seleccionada.

  • HELP; o HELP nombre_comando_sql;

    Proporciona ayuda sobre los comandos de MySQL. Ejemplo: HELP SELECT;

  • EXIT; (o QUIT; o \q)

    Cierra la conexión con el servidor MySQL y sale del cliente.

1.4.3. Creación de tu Primera Base de Datos y Tabla

Vamos a poner en práctica algunos de los comandos anteriores creando una base de datos simple y una tabla dentro de ella. Usaremos el cliente de línea de comandos mysql.

  1. Conéctate al servidor MySQL como root: 
    mysql -u root -p
    (Introduce tu contraseña de root).
  2. Crea una nueva base de datos llamada escuela: 
    mysql> CREATE DATABASE escuela;
    Puedes verificar que se creó con SHOW DATABASES;.
  3. Selecciona la base de datos escuela para usarla: 
    mysql> USE escuela;
  4. Crea una tabla llamada estudiantes con las siguientes columnas:
    • id: tipo INT, autoincremental, clave primaria.
    • nombre: tipo VARCHAR con una longitud máxima de 100 caracteres, no puede ser nulo.
    • email: tipo VARCHAR con una longitud máxima de 100 caracteres, debe ser único.
    • fecha_nacimiento: tipo DATE.
    El comando SQL sería: 
    mysql> CREATE TABLE estudiantes (
    ->     id INT AUTO_INCREMENT PRIMARY KEY,
    ->     nombre VARCHAR(100) NOT NULL,
    ->     email VARCHAR(100) UNIQUE,
    ->     fecha_nacimiento DATE
    -> );

    (El prompt -> indica que MySQL espera más líneas para el comando. Termina con ); y presiona Enter).

    Si todo va bien, verás: Query OK, 0 rows affected (...).
  5. Verifica que la tabla se creó: 
    mysql> SHOW TABLES;
    Deberías ver "estudiantes" en la lista.
  6. Inspecciona la estructura de la tabla estudiantes: 
    mysql> DESCRIBE estudiantes;
    O de forma más corta: 
    mysql> DESC estudiantes;
    Esto te mostrará las columnas, sus tipos, si pueden ser nulas, si son claves, etc. 
    +------------------+--------------+------+-----+---------+----------------+
| Field            | Type         | Null | Key | Default | Extra          |
+------------------+--------------+------+-----+---------+----------------+
| id               | int          | NO   | PRI | NULL    | auto_increment |
| nombre           | varchar(100) | NO   |     | NULL    |                |
| email            | varchar(100) | YES  | UNI | NULL    |                |
| fecha_nacimiento | date         | YES  |     | NULL    |                |
+------------------+--------------+------+-----+---------+----------------+
  7. Sal del cliente MySQL: 
    mysql> EXIT;

¡Felicidades! Has creado tu primera base de datos y tu primera tabla en MySQL. En las siguientes unidades aprenderemos a insertar datos en esta tabla y a consultarlos usando SQL.

2.1. Introducción a SQL

[Volver al Índice Principal]

2.1.1. ¿Qué es SQL? Estándares SQL.

SQL (Structured Query Language), pronunciado "ese-cu-ele" o a veces "sequel", es un lenguaje de dominio específico diseñado para administrar y consultar datos almacenados en Sistemas Gestores de Bases de Datos Relacionales (RDBMS). Es el lenguaje estándar de facto para interactuar con este tipo de bases de datos.

SQL permite realizar una amplia variedad de tareas, tales como:

  • Consultar datos (recuperar información).
  • Insertar nuevos datos.
  • Actualizar datos existentes.
  • Eliminar datos.
  • Crear, modificar y eliminar la estructura de la base de datos (tablas, índices, etc.).
  • Controlar el acceso a los datos (permisos).

Estándares SQL:

Para promover la portabilidad y la interoperabilidad entre diferentes SGBD, existen estándares SQL definidos por organismos como ANSI (American National Standards Institute) e ISO (International Organization for Standardization). El primer estándar ANSI SQL fue publicado en 1986, seguido por el estándar ISO en 1987.

Desde entonces, ha habido varias revisiones y extensiones del estándar, como SQL-92, SQL:1999, SQL:2003, SQL:2008, SQL:2011, SQL:2016 y SQL:2023. Cada nueva versión introduce nuevas características y funcionalidades.

Aunque los SGBD como MySQL, PostgreSQL, SQL Server y Oracle se esfuerzan por cumplir con estos estándares, cada uno también implementa sus propias extensiones y variaciones del lenguaje (a veces llamadas "dialectos" SQL). Esto significa que, si bien la mayoría de las sentencias SQL básicas funcionarán de manera similar en diferentes SGBD, algunas características avanzadas o sintaxis específicas pueden variar. MySQL, por ejemplo, sigue en gran medida el estándar SQL, pero también tiene sus propias funciones y sintaxis particulares.

2.1.2. Tipos de Comandos SQL (DDL, DML, DQL, DCL, TCL)

Los comandos SQL se pueden clasificar en varias categorías según su propósito:

  • DDL (Data Definition Language - Lenguaje de Definición de Datos):

    Se utilizan para definir o modificar la estructura de los objetos de la base de datos (como tablas, índices, vistas, etc.).

    Comandos principales:

    • CREATE: Para crear nuevos objetos (ej. CREATE TABLE, CREATE DATABASE, CREATE INDEX).
    • ALTER: Para modificar la estructura de objetos existentes (ej. ALTER TABLE).
    • DROP: Para eliminar objetos existentes (ej. DROP TABLE, DROP DATABASE).
    • TRUNCATE: Para eliminar todas las filas de una tabla rápidamente (es una operación DDL, no DML, porque es más similar a recrear la tabla vacía).
    • RENAME: Para renombrar un objeto.

  • DML (Data Manipulation Language - Lenguaje de Manipulación de Datos):

    Se utilizan para gestionar los datos dentro de los objetos de la base de datos (principalmente tablas).

    Comandos principales:

    • INSERT: Para añadir nuevas filas (registros) a una tabla.
    • UPDATE: Para modificar datos existentes en las filas de una tabla.
    • DELETE: Para eliminar filas de una tabla.

  • DQL (Data Query Language - Lenguaje de Consulta de Datos):

    Se utiliza para recuperar o consultar datos de la base de datos. Aunque a veces se considera una subcategoría de DML, es tan fundamental que a menudo se le da su propia clasificación.

    Comando principal:

    • SELECT: Para extraer datos de una o más tablas.

  • DCL (Data Control Language - Lenguaje de Control de Datos):

    Se utilizan para controlar el acceso a los datos y a la base de datos, es decir, para gestionar los permisos y la seguridad.

    Comandos principales:

    • GRANT: Para conceder permisos a los usuarios (ej. permiso para seleccionar datos de una tabla, permiso para crear tablas).
    • REVOKE: Para quitar permisos previamente concedidos a los usuarios.

  • TCL (Transaction Control Language - Lenguaje de Control de Transacciones):

    Se utilizan para gestionar las transacciones en la base de datos, asegurando la atomicidad y consistencia de las operaciones.

    Comandos principales:

    • COMMIT: Para guardar permanentemente los cambios realizados en una transacción.
    • ROLLBACK: Para deshacer los cambios realizados en una transacción si algo sale mal.
    • SAVEPOINT: Para establecer un punto dentro de una transacción al que se puede volver posteriormente con ROLLBACK TO SAVEPOINT.
    • SET TRANSACTION: Para especificar características de la transacción (ej. nivel de aislamiento).

En esta unidad nos centraremos principalmente en DDL, DML y DQL, que son los más fundamentales para el trabajo diario con datos.

2.2. DDL - Lenguaje de Definición de Datos

El Lenguaje de Definición de Datos (DDL) se utiliza para crear, modificar y eliminar la estructura de los objetos de la base de datos. Estos comandos afectan el "esquema" de la base de datos.

[Volver al Índice Principal]

2.2.1. CREATE DATABASE

Este comando se utiliza para crear una nueva base de datos (o esquema, que en MySQL es sinónimo de base de datos).

Sintaxis básica:

CREATE DATABASE nombre_de_la_base_de_datos;

Sintaxis con opciones (recomendado):

CREATE DATABASE IF NOT EXISTS nombre_de_la_base_de_datos
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;
  • IF NOT EXISTS: Esta cláusula opcional evita que se produzca un error si la base de datos ya existe. Simplemente no hará nada si ya existe.
  • CHARACTER SET: Especifica el conjunto de caracteres por defecto para la base de datos. utf8mb4 es altamente recomendado ya que soporta una amplia gama de caracteres, incluyendo emojis y la mayoría de los idiomas.
  • COLLATE: Especifica las reglas de cotejamiento (ordenación y comparación de cadenas) por defecto para la base de datos. utf8mb4_unicode_ci es una buena opción general para utf8mb4, ya que es insensible a mayúsculas/minúsculas (_ci) y sigue las reglas de Unicode.

Ejemplo:

CREATE DATABASE IF NOT EXISTS libreria_db
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_unicode_ci;
-- Query OK, 1 row affected (0.01 sec)

2.2.2. USE DATABASE

Una vez que una base de datos ha sido creada, necesitas seleccionarla para poder trabajar con sus tablas y otros objetos. El comando USE establece la base de datos activa para la sesión actual.

Sintaxis:

USE nombre_de_la_base_de_datos;

Ejemplo:

USE libreria_db;
-- Database changed

Después de ejecutar este comando, todas las sentencias SQL posteriores (como CREATE TABLE, SELECT, etc.) que no especifiquen explícitamente una base de datos, se aplicarán a libreria_db.

2.2.3. CREATE TABLE

El comando CREATE TABLE se utiliza para crear una nueva tabla dentro de la base de datos actualmente seleccionada.

Sintaxis básica:

CREATE TABLE nombre_de_la_tabla (
    nombre_columna1 tipo_de_dato [restricciones_columna1],
    nombre_columna2 tipo_de_dato [restricciones_columna2],
    ...
    [restricciones_tabla]
);
  • nombre_de_la_tabla: El nombre que le darás a la tabla.
  • nombre_columnaX: El nombre de cada columna.
  • tipo_de_dato: El tipo de datos que almacenará la columna (ver 2.2.3.1).
  • restricciones_columnaX: Reglas que se aplican a una columna individual (ver 2.2.3.2).
  • restricciones_tabla: Reglas que se aplican a nivel de tabla, como claves primarias compuestas o claves foráneas.

2.2.3.1. Tipos de Datos Comunes en MySQL (INT, VARCHAR, DATE, etc.)

MySQL ofrece una amplia variedad de tipos de datos para definir las columnas de tus tablas. Elegir el tipo de dato correcto es importante para la eficiencia del almacenamiento y la integridad de los datos.

Tipos Numéricos:

  • TINYINT: Entero muy pequeño. Rango: -128 a 127 (con signo) o 0 a 255 (UNSIGNED).
  • SMALLINT: Entero pequeño. Rango: -32768 a 32767 (con signo) o 0 a 65535 (UNSIGNED).
  • MEDIUMINT: Entero mediano.
  • INT o INTEGER: Entero estándar. Rango: -2147483648 a 2147483647 (con signo) o 0 a 4294967295 (UNSIGNED). Es el más común para IDs.
  • BIGINT: Entero grande. Para números muy grandes.
  • DECIMAL(M,D) o NUMERIC(M,D): Número de punto fijo exacto. M es el número total de dígitos (precisión) y D es el número de dígitos después del punto decimal (escala). Ideal para valores monetarios. Ej: DECIMAL(10,2).
  • FLOAT(M,D): Número de punto flotante de precisión simple. Aproximado.
  • DOUBLE(M,D) o REAL(M,D): Número de punto flotante de precisión doble. Aproximado.
  • BIT(M): Tipo para almacenar valores de bits (M de 1 a 64).
  • BOOL o BOOLEAN: Son sinónimos de TINYINT(1). Se usa 0 para falso y 1 para verdadero.

Tipos de Cadena (Texto):

  • CHAR(M): Cadena de longitud fija. M es la longitud (0 a 255). Siempre ocupa M bytes, rellenando con espacios si es necesario.
  • VARCHAR(M): Cadena de longitud variable. M es la longitud máxima (0 a 65535, aunque el límite efectivo depende de otros factores). Solo ocupa el espacio necesario más 1 o 2 bytes para la longitud. Es el más común para cadenas de texto.
  • TINYTEXT: Texto pequeño, hasta 255 caracteres.
  • TEXT: Texto, hasta 65,535 caracteres.
  • MEDIUMTEXT: Texto mediano, hasta 16,777,215 caracteres.
  • LONGTEXT: Texto largo, hasta 4,294,967,295 caracteres.
  • BINARY(M) y VARBINARY(M): Similares a CHAR y VARCHAR, pero almacenan cadenas de bytes binarios (sensibles a mayúsculas/minúsculas en comparaciones).
  • BLOB, TINYBLOB, MEDIUMBLOB, LONGBLOB: Para almacenar datos binarios grandes (Binary Large Objects), como imágenes o archivos.
  • ENUM('val1', 'val2', ...): Permite que una columna solo acepte uno de los valores de una lista predefinida. Ej: ENUM('activo', 'inactivo', 'pendiente').
  • SET('val1', 'val2', ...): Permite que una columna acepte cero, uno o más valores de una lista predefinida.

Tipos de Fecha y Hora:

  • DATE: Almacena una fecha en formato 'YYYY-MM-DD'.
  • TIME: Almacena una hora en formato 'HH:MM:SS'.
  • DATETIME: Almacena una combinación de fecha y hora en formato 'YYYY-MM-DD HH:MM:SS'.
  • TIMESTAMP: Similar a DATETIME, pero con un rango más limitado y características especiales como la actualización automática al valor actual si no se especifica. A menudo se usa para registrar cuándo se insertó o actualizó una fila.
  • YEAR: Almacena un año en formato de 2 o 4 dígitos.

Tipos Espaciales (Geométricos):

  • Para almacenar datos geográficos, como GEOMETRY, POINT, LINESTRING, POLYGON.

Tipo JSON (MySQL 5.7.8+):

  • JSON: Para almacenar datos en formato JSON (JavaScript Object Notation), con validación automática y funciones para manipular el contenido JSON.

Atributos Comunes de Columna:

  • UNSIGNED: Para tipos numéricos, indica que solo se almacenarán valores no negativos, duplicando el rango positivo.
  • ZEROFILL: Para tipos numéricos, rellena con ceros a la izquierda hasta alcanzar el ancho de visualización especificado para la columna (obsoleto y no recomendado para nuevas aplicaciones).

2.2.3.2. Restricciones (Constraints): NOT NULL, UNIQUE, PRIMARY KEY, DEFAULT, CHECK

Las restricciones (constraints) son reglas que se aplican a las columnas o tablas para asegurar la integridad y validez de los datos.

  • NOT NULL:

    Asegura que una columna no pueda contener valores NULL (ausencia de valor). Si se intenta insertar una fila sin un valor para una columna NOT NULL (y no tiene un valor DEFAULT), se producirá un error.

    nombre_columna tipo_de_dato NOT NULL
  • UNIQUE:

    Asegura que todos los valores en una columna (o un conjunto de columnas si se define a nivel de tabla) sean diferentes entre sí. Permite valores NULL (y múltiples NULLs, ya que NULL no es igual a NULL), a menos que la columna también sea NOT NULL.

    nombre_columna tipo_de_dato UNIQUE

    A nivel de tabla (para restricciones únicas multicolumna):

    CREATE TABLE mi_tabla (
    col1 INT,
    col2 INT,
    UNIQUE (col1, col2) -- La combinación de col1 y col2 debe ser única
);
  • PRIMARY KEY (Clave Primaria):

    Designa una columna (o un conjunto de columnas) como el identificador único principal para cada fila de la tabla. Una tabla solo puede tener una clave primaria.

    Una clave primaria implica automáticamente NOT NULL y UNIQUE.

    nombre_columna tipo_de_dato PRIMARY KEY

    Es muy común usarla con AUTO_INCREMENT para que MySQL genere automáticamente valores secuenciales para la clave primaria al insertar nuevas filas:

    id INT AUTO_INCREMENT PRIMARY KEY

    A nivel de tabla (para claves primarias compuestas):

    CREATE TABLE tabla_intermedia (
    id_tabla_A INT,
    id_tabla_B INT,
    PRIMARY KEY (id_tabla_A, id_tabla_B)
);
  • DEFAULT valor:

    Especifica un valor por defecto para una columna si no se proporciona un valor explícito durante una operación INSERT.

    fecha_registro DATE DEFAULT (CURDATE()) -- Usa la fecha actual como valor por defecto
estado VARCHAR(20) DEFAULT 'activo'

    Nota: En MySQL, para usar una función como `CURDATE()` como valor por defecto, a menudo se requiere que esté entre paréntesis a partir de ciertas versiones (ej., MySQL 8.0.13+).

  • CHECK (condición) (MySQL 8.0.16+):

    Permite definir una condición que debe ser verdadera para cualquier valor insertado o actualizado en la columna (o a nivel de tabla para condiciones que involucren múltiples columnas). Si la condición se evalúa como falsa, la operación se rechaza.

    precio DECIMAL(10,2) CHECK (precio > 0)
edad INT CHECK (edad >= 18)

    A nivel de tabla:

    CREATE TABLE eventos (
    fecha_inicio DATE,
    fecha_fin DATE,
    CHECK (fecha_fin >= fecha_inicio)
);
  • FOREIGN KEY (Clave Foránea): Se cubrirá en detalle en la Unidad 3, ya que se relaciona con las relaciones entre tablas.

Ejemplo de CREATE TABLE usando varios tipos y restricciones:

USE libreria_db; -- Asegúrate de tener la base de datos seleccionada

CREATE TABLE IF NOT EXISTS libros (
    isbn VARCHAR(17) PRIMARY KEY, -- ISBN como clave primaria (ej. '978-3-16-148410-0')
    titulo VARCHAR(255) NOT NULL,
    autor_id INT, -- Se relacionará con una tabla de autores más adelante
    editorial VARCHAR(100),
    fecha_publicacion DATE,
    precio DECIMAL(8,2) CHECK (precio >= 0),
    stock INT DEFAULT 0 CHECK (stock >= 0),
    idioma VARCHAR(50) DEFAULT 'Español',
    descripcion TEXT,
    fecha_alta TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

2.2.4. ALTER TABLE (ADD, DROP, MODIFY COLUMN, etc.)

El comando ALTER TABLE se utiliza para modificar la estructura de una tabla existente. Permite añadir, eliminar o modificar columnas, así como añadir o eliminar restricciones.

Sintaxis comunes:

  • Añadir una columna: 
    ALTER TABLE nombre_de_la_tabla
ADD COLUMN nombre_nueva_columna tipo_de_dato [restricciones] [AFTER otra_columna | FIRST];

    Ejemplo: Añadir una columna `genero` a la tabla `libros`.

    ALTER TABLE libros
ADD COLUMN genero VARCHAR(50) AFTER editorial;
  • Eliminar una columna: 
    ALTER TABLE nombre_de_la_tabla
DROP COLUMN nombre_columna_a_eliminar;

    Ejemplo: Eliminar la columna `idioma` de la tabla `libros`.

    ALTER TABLE libros
DROP COLUMN idioma;
  • Modificar el tipo de dato o restricciones de una columna: 
    ALTER TABLE nombre_de_la_tabla
MODIFY COLUMN nombre_columna nuevo_tipo_de_dato [nuevas_restricciones];

    Ejemplo: Cambiar el `titulo` de la tabla `libros` para que sea más corto y siempre NOT NULL.

    ALTER TABLE libros
MODIFY COLUMN titulo VARCHAR(200) NOT NULL;
  • Renombrar una columna y opcionalmente cambiar su definición: 
    ALTER TABLE nombre_de_la_tabla
CHANGE COLUMN nombre_columna_antiguo nombre_columna_nuevo nuevo_tipo_de_dato [nuevas_restricciones];

    Ejemplo: Renombrar `fecha_alta` a `creado_en` y mantener su tipo y default.

    ALTER TABLE libros
CHANGE COLUMN fecha_alta creado_en TIMESTAMP DEFAULT CURRENT_TIMESTAMP;
  • Añadir una restricción (ej. UNIQUE, CHECK): 
    ALTER TABLE nombre_de_la_tabla
ADD CONSTRAINT nombre_de_la_restriccion UNIQUE (nombre_columna);
    ALTER TABLE nombre_de_la_tabla
ADD CONSTRAINT nombre_de_la_restriccion CHECK (condicion);

    Ejemplo: Añadir una restricción única a la combinación de `titulo` y `autor_id`.

    ALTER TABLE libros
ADD CONSTRAINT uq_titulo_autor UNIQUE (titulo, autor_id);
  • Eliminar una restricción:

    Para claves primarias, foráneas o únicas, se usa DROP PRIMARY KEY, DROP FOREIGN KEY nombre_fk, DROP INDEX nombre_indice_unique (o DROP CONSTRAINT nombre_restriccion_unique).

    Para restricciones CHECK (MySQL 8.0.16+):

    ALTER TABLE nombre_de_la_tabla
DROP CHECK nombre_de_la_restriccion_check;

    Ejemplo: Eliminar la restricción uq_titulo_autor (el nombre es importante).

    ALTER TABLE libros
DROP INDEX uq_titulo_autor; -- Las restricciones UNIQUE suelen crear un índice con el mismo nombre
  • Renombrar una tabla: 
    ALTER TABLE nombre_tabla_antiguo
RENAME TO nombre_tabla_nuevo;
    O también: 
    RENAME TABLE nombre_tabla_antiguo TO nombre_tabla_nuevo;

ALTER TABLE es un comando potente pero debe usarse con cuidado, especialmente en tablas grandes con datos, ya que algunas operaciones pueden ser lentas y bloquear la tabla.

[Volver al Índice Principal]

2.2.5. DROP TABLE

El comando DROP TABLE se utiliza para eliminar una tabla existente de la base de datos. Esta operación es irreversible y elimina tanto la estructura de la tabla como todos los datos que contenía.

Sintaxis:

DROP TABLE [IF EXISTS] nombre_de_la_tabla;
  • IF EXISTS: Cláusula opcional que evita que se produzca un error si la tabla no existe.

Ejemplo:

DROP TABLE IF EXISTS libros_temporales;
-- Query OK, 0 rows affected (0.01 sec) (si no existía o si se borró)

¡ADVERTENCIA! Usa DROP TABLE con extrema precaución. Asegúrate de que realmente quieres eliminar la tabla y sus datos, ya que no hay una forma fácil de recuperarlos una vez eliminados (a menos que tengas copias de seguridad).

[Volver al Índice Principal]

2.2.6. TRUNCATE TABLE

El comando TRUNCATE TABLE se utiliza para eliminar todas las filas de una tabla de forma muy rápida. A diferencia de DELETE FROM nombre_tabla (sin cláusula WHERE), que elimina las filas una por una y registra cada eliminación (lo que puede ser lento para tablas grandes y genera mucha actividad en el log de transacciones), TRUNCATE TABLE es generalmente más rápido porque suele funcionar desasignando las páginas de datos de la tabla y reseteando el contador AUTO_INCREMENT (si lo hay).

Sintaxis:

TRUNCATE TABLE nombre_de_la_tabla;

Características y Diferencias con DELETE:

  • Velocidad: Mucho más rápido que DELETE para tablas grandes.
  • Log de Transacciones: Genera menos actividad en el log de transacciones.
  • AUTO_INCREMENT: Resetea el valor de AUTO_INCREMENT al valor inicial.
  • Triggers: No dispara los triggers ON DELETE que pudiera tener la tabla.
  • Rollback: No se puede hacer ROLLBACK de una operación TRUNCATE si la sesión no está dentro de una transacción explícita (y aún así, el comportamiento puede variar según el motor y la configuración). Generalmente se considera una operación DDL y no DML en este sentido.
  • Permisos: Requiere el permiso DROP sobre la tabla, mientras que DELETE requiere el permiso DELETE.

Ejemplo:

TRUNCATE TABLE logs_aplicacion;
-- Query OK, 0 rows affected (0.02 sec)

Usa TRUNCATE TABLE cuando quieras vaciar completamente una tabla y no necesites la granularidad o las características transaccionales de DELETE.

[Volver al Índice Principal]

2.2.7. DROP DATABASE

El comando DROP DATABASE se utiliza para eliminar una base de datos completa, incluyendo todas sus tablas, índices, vistas y otros objetos, así como todos los datos que contenían.

Sintaxis:

DROP DATABASE [IF EXISTS] nombre_de_la_base_de_datos;
  • IF EXISTS: Cláusula opcional que evita un error si la base de datos no existe.

Ejemplo:

DROP DATABASE IF EXISTS base_de_datos_de_prueba;
-- Query OK, X rows affected (donde X es el número de tablas eliminadas)

¡ADVERTENCIA MÁXIMA! Este es uno de los comandos más destructivos. Una vez ejecutado, todos los datos y la estructura de la base de datos se pierden permanentemente (a menos que existan copias de seguridad). Úsalo con extrema precaución y asegúrate de estar en el servidor y la base de datos correctos.

2.3. DML - Lenguaje de Manipulación de Datos

El Lenguaje de Manipulación de Datos (DML) se utiliza para insertar, actualizar y eliminar datos dentro de las tablas de una base de datos.

Para los siguientes ejemplos, asumiremos que tenemos la tabla estudiantes que creamos en la Unidad 1, y la base de datos escuela está seleccionada con USE escuela;.

-- Estructura de la tabla estudiantes para referencia:
-- CREATE TABLE estudiantes (
--     id INT AUTO_INCREMENT PRIMARY KEY,
--     nombre VARCHAR(100) NOT NULL,
--     email VARCHAR(100) UNIQUE,
--     fecha_nacimiento DATE
-- );

[Volver al Índice Principal]

2.3.1. INSERT INTO

El comando INSERT INTO se utiliza para añadir nuevas filas (registros) a una tabla.

Sintaxis 1: Especificando columnas y valores (recomendada por su claridad)

INSERT INTO nombre_de_la_tabla (columna1, columna2, columna3, ...)
VALUES (valor1, valor2, valor3, ...);
  • El orden de los valores en la cláusula VALUES debe corresponder al orden de las columnas especificadas.
  • Las cadenas de texto y las fechas suelen ir entre comillas simples (' ').

Ejemplo 1: Insertar un estudiante

INSERT INTO estudiantes (nombre, email, fecha_nacimiento)
VALUES ('Ana Pérez', 'ana.perez@example.com', '2002-05-15');
-- Query OK, 1 row affected (0.01 sec)

Sintaxis 2: Sin especificar columnas (se asumen todas las columnas en su orden de definición) (menos recomendada, propensa a errores si la tabla cambia)

INSERT INTO nombre_de_la_tabla
VALUES (valor_para_col1, valor_para_col2, valor_para_col3, ...);

Si una columna es AUTO_INCREMENT (como id en nuestra tabla), puedes pasar NULL o DEFAULT para que MySQL genere el valor, o simplemente omitirla si usas la Sintaxis 1 y no la incluyes en la lista de columnas.

Ejemplo 2: Insertar otro estudiante omitiendo el ID (se autogenerará)

INSERT INTO estudiantes (nombre, email, fecha_nacimiento)
VALUES ('Luis García', 'luis.garcia@example.com', '2001-11-20');

Insertar Múltiples Filas:

Puedes insertar varias filas con una sola sentencia INSERT INTO separando las tuplas de valores con comas:

INSERT INTO estudiantes (nombre, email, fecha_nacimiento) VALUES
    ('Carlos López', 'carlos.lopez@example.com', '2003-01-10'),
    ('Sofía Martín', 'sofia.martin@example.com', '2002-09-05'),
    ('Javier Ruiz', 'javier.ruiz@example.com', NULL); -- Fecha de nacimiento opcional (permite NULL)

Insertar con valor por defecto o NULL explícito:

Si una columna tiene un valor DEFAULT definido o permite NULL, puedes usar la palabra clave DEFAULT o NULL explícitamente.

-- Suponiendo que 'email' no tuviera restricción UNIQUE y tuviera un DEFAULT
-- INSERT INTO estudiantes (nombre, email) VALUES ('Pedro Sin Email', DEFAULT);
INSERT INTO estudiantes (nombre, fecha_nacimiento) VALUES ('Marta Temporal', '1999-12-01'); -- Email será NULL

[Volver al Índice Principal]

2.3.2. UPDATE

El comando UPDATE se utiliza para modificar datos existentes en las filas de una tabla.

Sintaxis:

UPDATE nombre_de_la_tabla
SET columna1 = nuevo_valor1,
    columna2 = nuevo_valor2,
    ...
WHERE condicion;
  • SET: Especifica las columnas que se van a actualizar y sus nuevos valores.
  • WHERE: ¡Cláusula crucial! Especifica qué filas deben ser actualizadas. Si omites la cláusula WHERE, ¡todas las filas de la tabla serán actualizadas! Esto es raramente lo que se desea y puede ser muy destructivo.

Ejemplo 1: Actualizar el email de Ana Pérez (suponiendo que su ID es 1)

UPDATE estudiantes
SET email = 'ana.p.actualizado@example.com'
WHERE id = 1;
-- Query OK, 1 row affected (0.01 sec)
-- Rows matched: 1  Changed: 1  Warnings: 0

Ejemplo 2: Actualizar la fecha de nacimiento de todos los estudiantes llamados 'Carlos López'

UPDATE estudiantes
SET fecha_nacimiento = '2003-02-15'
WHERE nombre = 'Carlos López';

Ejemplo 3: Incrementar un valor (si tuviéramos una columna `creditos`)

-- UPDATE estudiantes SET creditos = creditos + 10 WHERE id = 2;

Actualizar Múltiples Columnas:

UPDATE estudiantes
SET nombre = 'Luis Miguel García', email = 'luismiguel.g@example.com'
WHERE id = 2;

Recuerda siempre verificar tu cláusula WHERE antes de ejecutar un UPDATE, especialmente en entornos de producción. Una buena práctica es ejecutar primero un SELECT con la misma condición WHERE para asegurarte de que estás seleccionando las filas correctas.

2.3.3. DELETE FROM

El comando DELETE FROM se utiliza para eliminar filas de una tabla.

Sintaxis:

DELETE FROM nombre_de_la_tabla
WHERE condicion;
  • WHERE: ¡Cláusula crucial! Especifica qué filas deben ser eliminadas. Si omites la cláusula WHERE, ¡todas las filas de la tabla serán eliminadas!

Ejemplo 1: Eliminar al estudiante con email 'javier.ruiz@example.com'

DELETE FROM estudiantes
WHERE email = 'javier.ruiz@example.com';
-- Query OK, 1 row affected (0.01 sec) (si existía)

Ejemplo 2: Eliminar a todos los estudiantes cuya fecha de nacimiento sea anterior a '2000-01-01'

DELETE FROM estudiantes
WHERE fecha_nacimiento < '2000-01-01';

Ejemplo 3: Eliminar todas las filas de la tabla (¡PELIGROSO!)

-- DELETE FROM estudiantes; -- ¡Esto borraría todos los estudiantes!

Al igual que con UPDATE, siempre verifica tu cláusula WHERE con un SELECT antes de ejecutar un DELETE en producción. Si quieres eliminar todas las filas y resetear contadores AUTO_INCREMENT, considera usar TRUNCATE TABLE (ver 2.2.6), pero ten en cuenta sus diferencias.

2.4.1. SELECT Básico (*, Nombres de Columnas, Alias)

La sentencia SELECT es la herramienta fundamental para extraer datos.

Seleccionar todas las columnas de todas las filas:

El asterisco (*) se utiliza como comodín para seleccionar todas las columnas de la tabla.

SELECT * FROM estudiantes;

Seleccionar columnas específicas:

Es más eficiente y claro especificar solo las columnas que necesitas.

SELECT nombre, email FROM estudiantes;

Uso de Alias para Columnas (AS):

Puedes renombrar las columnas en el resultado de la consulta usando la palabra clave AS. Esto es útil para hacer los resultados más legibles o para evitar conflictos de nombres en consultas complejas.

SELECT
    nombre AS nombre_completo,
    email AS correo_electronico,
    fecha_nacimiento AS f_nac
FROM estudiantes;

La palabra clave AS es opcional para los alias de columna en muchos SGBD (incluido MySQL), pero se recomienda por claridad:

SELECT nombre nombre_completo, email correo_electronico FROM estudiantes;

2.4.2. Cláusula WHERE y Operadores de Comparación

La cláusula WHERE se utiliza para filtrar las filas devueltas por la consulta, seleccionando solo aquellas que cumplen una condición específica.

Operadores de Comparación Comunes:

  • = : Igual a
  • <> o != : Diferente de
  • < : Menor que
  • > : Mayor que
  • <= : Menor o igual que
  • >= : Mayor o igual que

Ejemplo 1: Seleccionar estudiantes nacidos después del '2002-01-01'

SELECT nombre, fecha_nacimiento
FROM estudiantes
WHERE fecha_nacimiento > '2002-01-01';

Ejemplo 2: Seleccionar al estudiante con el email 'carlos.lopez@example.com'

SELECT *
FROM estudiantes
WHERE email = 'carlos.lopez@example.com';

Ejemplo 3: Seleccionar estudiantes cuyo ID no sea 1

SELECT id, nombre
FROM estudiantes
WHERE id <> 1;

2.4.3. Operadores Lógicos (AND, OR, NOT) y Paréntesis

Los operadores lógicos permiten combinar múltiples condiciones en la cláusula WHERE.

  • AND: Ambas condiciones deben ser verdaderas.
  • OR: Al menos una de las condiciones debe ser verdadera.
  • NOT: Niega una condición (la invierte).

Los paréntesis () se utilizan para agrupar condiciones y controlar el orden de evaluación (AND tiene mayor precedencia que OR por defecto).

Ejemplo 1: Estudiantes llamados 'Ana Pérez' Y nacidos en '2002-05-15'

SELECT * FROM estudiantes
WHERE nombre = 'Ana Pérez' AND fecha_nacimiento = '2002-05-15';

Ejemplo 2: Estudiantes llamados 'Sofía Martín' O 'Carlos López'

SELECT * FROM estudiantes
WHERE nombre = 'Sofía Martín' OR nombre = 'Carlos López';

Ejemplo 3: Estudiantes que NO se llaman 'Ana Pérez'

SELECT * FROM estudiantes
WHERE NOT nombre = 'Ana Pérez';

O también (más común):

SELECT * FROM estudiantes
WHERE nombre <> 'Ana Pérez';

Ejemplo 4: Uso de paréntesis para controlar la precedencia

Seleccionar estudiantes que se llamen 'Ana Pérez' O ('Luis Miguel García' Y nacidos antes de '2002-01-01').

SELECT * FROM estudiantes
WHERE nombre = 'Ana Pérez' OR (nombre = 'Luis Miguel García' AND fecha_nacimiento < '2002-01-01');

2.4.4. Operadores Especiales (BETWEEN, LIKE, IN, IS NULL)

SQL proporciona operadores especiales para simplificar ciertos tipos de condiciones:

  • BETWEEN ... AND ...:

    Selecciona valores dentro de un rango (incluyendo los límites).

    Ejemplo: Estudiantes nacidos entre '2002-01-01' y '2002-12-31'.

    SELECT nombre, fecha_nacimiento FROM estudiantes
WHERE fecha_nacimiento BETWEEN '2002-01-01' AND '2002-12-31';
  • LIKE:

    Se utiliza para la comparación de patrones en cadenas de texto. Utiliza comodines:

    • %: Representa cero, uno o múltiples caracteres.
    • _: Representa un único carácter.

    Ejemplo: Estudiantes cuyo nombre empieza con 'A'.

    SELECT nombre FROM estudiantes
WHERE nombre LIKE 'A%';

    Ejemplo: Estudiantes cuyo email contiene 'garcia'.

    SELECT email FROM estudiantes
WHERE email LIKE '%garcia%';

    Ejemplo: Estudiantes cuyo nombre tiene 'u' como segundo carácter y 's' como cuarto.

    SELECT nombre FROM estudiantes
WHERE nombre LIKE '_u_s%';

    Para buscar los caracteres % o _ literalmente, se pueden escapar con ESCAPE (ej. LIKE '10\%%' ESCAPE '\').

  • IN (valor1, valor2, ...):

    Comprueba si el valor de una columna coincide con alguno de los valores de una lista.

    Ejemplo: Estudiantes llamados 'Ana Pérez' o 'Sofía Martín'.

    SELECT * FROM estudiantes
WHERE nombre IN ('Ana Pérez', 'Sofía Martín');

    Es equivalente a (nombre = 'Ana Pérez' OR nombre = 'Sofía Martín') pero más conciso.

  • IS NULL / IS NOT NULL:

    Comprueba si el valor de una columna es NULL (ausencia de valor) o no es NULL. No se puede usar = NULL o <> NULL.

    Ejemplo: Estudiantes que tienen un email registrado (no nulo).

    SELECT nombre, email FROM estudiantes
WHERE email IS NOT NULL;

    Ejemplo: Estudiantes sin email registrado (email es nulo).

    SELECT nombre, email FROM estudiantes
WHERE email IS NULL;

2.4.5. Cláusula ORDER BY (ASC, DESC)

La cláusula ORDER BY se utiliza para ordenar las filas del resultado de la consulta según una o más columnas.

  • ASC: Orden ascendente (A-Z, 0-9, fecha más antigua a más reciente). Es el valor por defecto si no se especifica.
  • DESC: Orden descendente (Z-A, 9-0, fecha más reciente a más antigua).

Ejemplo 1: Ordenar estudiantes por nombre alfabéticamente (ascendente)

SELECT * FROM estudiantes
ORDER BY nombre ASC;

O simplemente (ASC es el default):

SELECT * FROM estudiantes
ORDER BY nombre;

Ejemplo 2: Ordenar estudiantes por fecha de nacimiento, del más joven al más viejo (descendente)

SELECT * FROM estudiantes
ORDER BY fecha_nacimiento DESC;

Ordenar por Múltiples Columnas:

Se puede ordenar por una columna y, si hay empates, por una segunda columna, y así sucesivamente.

Ejemplo: Ordenar por fecha de nacimiento (descendente) y luego por nombre (ascendente) para los que tengan la misma fecha.

SELECT * FROM estudiantes
ORDER BY fecha_nacimiento DESC, nombre ASC;

También se puede ordenar por la posición de la columna en la lista SELECT (aunque es menos legible y propenso a errores si la lista SELECT cambia):

SELECT id, nombre, email FROM estudiantes
ORDER BY 2; -- Ordena por la segunda columna (nombre)

2.4.6. Cláusula LIMIT y OFFSET (Paginación)

La cláusula LIMIT se utiliza para restringir el número de filas devueltas por la consulta.

Sintaxis básica de LIMIT:

SELECT columnas FROM tabla
[WHERE condicion]
[ORDER BY columna]
LIMIT numero_de_filas;

Ejemplo: Obtener los 3 primeros estudiantes (según el orden por defecto de la tabla o el ORDER BY si se usa)

SELECT * FROM estudiantes
LIMIT 3;

Paginación con LIMIT y OFFSET:

OFFSET (o la sintaxis LIMIT offset, count en MySQL) permite saltar un número de filas antes de empezar a devolver resultados. Esto es fundamental para implementar la paginación en aplicaciones.

Sintaxis con OFFSET (Estándar SQL, soportado en MySQL):

SELECT columnas FROM tabla
LIMIT numero_de_filas OFFSET numero_de_filas_a_saltar;

Sintaxis alternativa en MySQL (LIMIT offset, count):

SELECT columnas FROM tabla
LIMIT numero_de_filas_a_saltar, numero_de_filas;

Ejemplo: Paginación - Obtener la segunda página de 2 estudiantes por página (es decir, estudiantes 3 y 4), ordenados por ID.

  • Página 1: LIMIT 2 OFFSET 0 (o LIMIT 0, 2)
  • Página 2: LIMIT 2 OFFSET 2 (o LIMIT 2, 2)
  • Página 3: LIMIT 2 OFFSET 4 (o LIMIT 4, 2)

Usando la sintaxis LIMIT offset, count para obtener la página 2:

SELECT * FROM estudiantes
ORDER BY id
LIMIT 2, 2; -- Salta 2 filas, devuelve las siguientes 2

Es muy importante usar ORDER BY con LIMIT para paginación para asegurar un orden consistente de los resultados entre páginas.

2.4.7. Funciones de Agregación (COUNT, SUM, AVG, MIN, MAX)

Las funciones de agregación operan sobre un conjunto de valores (generalmente una columna) y devuelven un único valor resumido.

  • COUNT(expresion):

    Cuenta el número de filas.

    • COUNT(*): Cuenta todas las filas que cumplen la condición WHERE (si la hay).
    • COUNT(nombre_columna): Cuenta el número de filas donde nombre_columna no es NULL.
    • COUNT(DISTINCT nombre_columna): Cuenta el número de valores únicos no nulos en nombre_columna.

    SELECT COUNT(*) AS total_estudiantes FROM estudiantes;
SELECT COUNT(email) AS estudiantes_con_email FROM estudiantes;
  • SUM(nombre_columna):

    Calcula la suma de los valores (numéricos) de una columna.

    -- Suponiendo una tabla 'pedidos' con una columna 'total_pedido'
-- SELECT SUM(total_pedido) AS ventas_totales FROM pedidos;
  • AVG(nombre_columna):

    Calcula el promedio de los valores (numéricos) de una columna.

    -- Suponiendo una tabla 'productos' con una columna 'precio'
-- SELECT AVG(precio) AS precio_promedio FROM productos;
  • MIN(nombre_columna):

    Encuentra el valor mínimo en una columna.

    SELECT MIN(fecha_nacimiento) AS estudiante_mas_mayor FROM estudiantes;
  • MAX(nombre_columna):

    Encuentra el valor máximo en una columna.

    SELECT MAX(fecha_nacimiento) AS estudiante_mas_joven FROM estudiantes;

Las funciones de agregación suelen usarse con la cláusula GROUP BY para realizar cálculos por grupos.

2.4.8. Cláusula GROUP BY

La cláusula GROUP BY se utiliza para agrupar filas que tienen los mismos valores en una o más columnas. Se usa casi siempre en conjunto con funciones de agregación para calcular métricas para cada grupo.

Regla importante: Si usas GROUP BY, cualquier columna en la lista SELECT que no esté en una función de agregación debe estar incluida en la cláusula GROUP BY.

Ejemplo 1: Contar cuántos estudiantes nacieron en cada año.

Primero, necesitamos una forma de extraer el año de `fecha_nacimiento`. MySQL tiene la función `YEAR()`.

SELECT
    YEAR(fecha_nacimiento) AS anio_nacimiento,
    COUNT(*) AS total_estudiantes_por_anio
FROM estudiantes
WHERE fecha_nacimiento IS NOT NULL -- Solo consideramos los que tienen fecha
GROUP BY anio_nacimiento -- o GROUP BY YEAR(fecha_nacimiento)
ORDER BY anio_nacimiento;

Cuando agrupas, el resultado es una fila por cada grupo único.

2.4.9. Cláusula HAVING

La cláusula HAVING se utiliza para filtrar grupos creados por la cláusula GROUP BY. Mientras que WHERE filtra filas antes de que se formen los grupos, HAVING filtra después de que los grupos se han formado y las funciones de agregación se han calculado.

Por lo tanto, en la cláusula HAVING puedes usar funciones de agregación, pero en la cláusula WHERE no (o al menos no directamente sobre el resultado de la agregación).

Sintaxis:

SELECT columnas_y_agregaciones
FROM tabla
[WHERE condicion_filas]
GROUP BY columnas_agrupacion
HAVING condicion_grupos
[ORDER BY columnas_orden];

Ejemplo: Mostrar los años de nacimiento en los que nacieron más de 1 estudiante.

SELECT
    YEAR(fecha_nacimiento) AS anio_nacimiento,
    COUNT(*) AS total_estudiantes
FROM estudiantes
WHERE fecha_nacimiento IS NOT NULL
GROUP BY anio_nacimiento
HAVING COUNT(*) > 1 -- Condición sobre el resultado de la agregación
ORDER BY anio_nacimiento;

No podrías poner WHERE COUNT(*) > 1 porque WHERE se evalúa antes de GROUP BY y COUNT(*).

2.4.10. Cláusula DISTINCT

La cláusula DISTINCT se utiliza con SELECT para eliminar filas duplicadas del conjunto de resultados. Solo devuelve filas únicas basadas en las columnas especificadas.

Sintaxis:

SELECT DISTINCT columna1, columna2, ...
FROM nombre_de_la_tabla;

DISTINCT se aplica a todas las columnas listadas en el SELECT. Una fila se considera duplicada si todos los valores de las columnas seleccionadas son idénticos a los de otra fila.

Ejemplo 1: Obtener una lista de todos los nombres únicos de estudiantes.

Si hubiera varios estudiantes con el mismo nombre, solo aparecería una vez.

SELECT DISTINCT nombre
FROM estudiantes
ORDER BY nombre;

Ejemplo 2: Obtener combinaciones únicas de año de nacimiento y nombre.

SELECT DISTINCT YEAR(fecha_nacimiento) AS anio_nacimiento, nombre
FROM estudiantes
WHERE fecha_nacimiento IS NOT NULL
ORDER BY anio_nacimiento, nombre;

DISTINCT puede ser útil, pero a veces un uso excesivo puede indicar un diseño de consulta o de tabla que podría mejorarse, especialmente si se usa sin una comprensión clara de por qué existen duplicados.

COUNT(DISTINCT nombre_columna), como se vio en las funciones de agregación, es un uso común de DISTINCT para contar valores únicos.

3.1. Relaciones entre Tablas

En una base de datos relacional, los datos se distribuyen en múltiples tablas para evitar la redundancia y mejorar la organización (proceso conocido como normalización). Las relaciones entre estas tablas se establecen mediante claves foráneas.

[Volver al Índice Principal]

3.1.1. Concepto de Clave Foránea (Foreign Key)

Una clave foránea (Foreign Key - FK) es una columna o un conjunto de columnas en una tabla (la tabla "hija" o "referenciante") cuyos valores deben coincidir con los valores de la clave primaria (Primary Key - PK) de otra tabla (la tabla "padre" o "referenciada").

Las claves foráneas son el mecanismo fundamental para:

  • Establecer relaciones lógicas entre diferentes entidades representadas en tablas.
  • Mantener la integridad referencial: Aseguran que no se puedan insertar filas en la tabla hija con valores en la FK que no existan en la PK de la tabla padre. También controlan qué sucede con las filas hijas cuando se elimina o actualiza una fila en la tabla padre.

Ejemplo:

Imagina que tenemos una tabla clientes con una columna id_cliente (PK) y una tabla pedidos. Para saber qué cliente realizó cada pedido, la tabla pedidos tendría una columna id_cliente_fk que sería una clave foránea referenciando a clientes(id_cliente).

-- Tabla Padre
CREATE TABLE clientes (
    id_cliente INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE
);

-- Tabla Hija (con la clave foránea)
CREATE TABLE pedidos (
    id_pedido INT AUTO_INCREMENT PRIMARY KEY,
    id_cliente_fk INT, -- Esta columna almacenará el ID del cliente que hizo el pedido
    fecha_pedido DATE NOT NULL,
    total_pedido DECIMAL(10, 2),
    FOREIGN KEY (id_cliente_fk) REFERENCES clientes(id_cliente)
);

En este caso, no podrías insertar un pedido con un id_cliente_fk que no exista en la tabla clientes.

[Volver al Índice Principal]

3.1.2. Tipos de Relaciones (Uno a Uno, Uno a Muchos, Muchos a Muchos)

Las relaciones entre tablas se pueden clasificar según la cardinalidad, es decir, cuántas instancias de una entidad pueden estar relacionadas con cuántas instancias de otra entidad.

  • Relación Uno a Uno (1:1):

    Cada fila en la Tabla A se relaciona con como máximo una fila en la Tabla B, y viceversa. Este tipo de relación es menos común. A veces se usa para dividir una tabla grande en partes más pequeñas por razones de rendimiento o seguridad, o para aislar datos opcionales.

    Implementación: Se establece una clave foránea en una de las tablas que referencia la clave primaria de la otra. Para asegurar la unicidad en la tabla que contiene la FK, se puede añadir una restricción UNIQUE a la columna de la FK.

    Ejemplo: Una tabla empleados y una tabla detalles_empleado_confidencial. Cada empleado tiene un solo conjunto de detalles confidenciales.

    CREATE TABLE empleados (
    id_empleado INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(100)
);

CREATE TABLE detalles_empleado_confidencial (
    id_empleado_fk INT PRIMARY KEY, -- Usar la FK como PK asegura la relación 1:1
    numero_seguridad_social VARCHAR(20) UNIQUE,
    salario DECIMAL(10,2),
    FOREIGN KEY (id_empleado_fk) REFERENCES empleados(id_empleado) ON DELETE CASCADE
);
  • Relación Uno a Muchos (1:N) o Muchos a Uno (N:1):

    Una fila en la Tabla A (la del "uno") se puede relacionar con muchas filas en la Tabla B (la de los "muchos"), pero cada fila en la Tabla B se relaciona con solo una fila en la Tabla A. Este es el tipo de relación más común.

    Implementación: Se añade una clave foránea en la tabla del lado "muchos" que referencia la clave primaria de la tabla del lado "uno".

    Ejemplo: Un cliente (Tabla A, lado "uno") puede tener muchos pedidos (Tabla B, lado "muchos"). Cada pedido pertenece a un solo cliente. (Como el ejemplo de clientes y pedidos anterior).

  • Relación Muchos a Muchos (N:M):

    Una fila en la Tabla A puede relacionarse con muchas filas en la Tabla B, y una fila en la Tabla B también puede relacionarse con muchas filas en la Tabla A.

    Implementación: Este tipo de relación no se puede implementar directamente con una sola clave foránea. Se requiere una tercera tabla, llamada tabla de unión, tabla intermedia, tabla de enlace o tabla asociativa. Esta tabla intermedia tendrá al menos dos claves foráneas, cada una referenciando la clave primaria de una de las tablas originales. La combinación de estas dos claves foráneas suele formar la clave primaria de la tabla intermedia.

    Ejemplo: estudiantes y cursos. Un estudiante puede estar inscrito en muchos cursos, y un curso puede tener muchos estudiantes.

    CREATE TABLE estudiantes (
    id_estudiante INT AUTO_INCREMENT PRIMARY KEY,
    nombre_estudiante VARCHAR(100)
);

CREATE TABLE cursos (
    id_curso INT AUTO_INCREMENT PRIMARY KEY,
    nombre_curso VARCHAR(100)
);

-- Tabla intermedia para la relación N:M
CREATE TABLE estudiantes_cursos (
    id_estudiante_fk INT,
    id_curso_fk INT,
    fecha_inscripcion DATE,
    PRIMARY KEY (id_estudiante_fk, id_curso_fk), -- Clave primaria compuesta
    FOREIGN KEY (id_estudiante_fk) REFERENCES estudiantes(id_estudiante) ON DELETE CASCADE,
    FOREIGN KEY (id_curso_fk) REFERENCES cursos(id_curso) ON DELETE CASCADE
);

3.1.3. Creación de Tablas con Claves Foráneas

Ya hemos visto ejemplos, pero repasemos la sintaxis para definir una clave foránea al crear una tabla.

Sintaxis:

CREATE TABLE nombre_tabla_hija (
    columna1 tipo_dato,
    ...,
    columna_fk tipo_dato_fk, -- Debe ser del mismo tipo que la PK referenciada
    ...,
    -- Definición de la clave foránea a nivel de tabla (más común)
    [CONSTRAINT nombre_opcional_fk] -- Dar un nombre a la restricción es buena práctica
    FOREIGN KEY (columna_fk) REFERENCES nombre_tabla_padre(columna_pk_padre)
    [ON DELETE accion_referencial]
    [ON UPDATE accion_referencial]
);

[Volver al Índice Principal]

3.1.3.1. REFERENCES y ON DELETE / ON UPDATE

La cláusula REFERENCES nombre_tabla_padre(columna_pk_padre) especifica la tabla y la columna (clave primaria) a la que se refiere la clave foránea.

Las cláusulas opcionales ON DELETE y ON UPDATE definen las acciones referenciales, es decir, qué debe suceder en la tabla hija (la que contiene la FK) cuando una fila referenciada en la tabla padre es eliminada (ON DELETE) o su clave primaria es actualizada (ON UPDATE, aunque actualizar claves primarias es generalmente una mala práctica y se evita).

Acciones Referenciales Comunes:

  • RESTRICT (Comportamiento por defecto en InnoDB si no se especifica):

    Impide la eliminación o actualización de la fila en la tabla padre si existen filas relacionadas en la tabla hija. La operación en la tabla padre fallará con un error.

  • NO ACTION:

    Similar a RESTRICT en MySQL. La comprobación se realiza al final de la sentencia (o transacción, dependiendo del SGBD y configuración), pero en la práctica, en InnoDB, se comporta igual que RESTRICT.

  • CASCADE:
    • ON DELETE CASCADE: Si se elimina una fila en la tabla padre, todas las filas relacionadas en la tabla hija (que referencian esa fila padre) también se eliminan automáticamente.
    • ON UPDATE CASCADE: Si se actualiza el valor de la clave primaria en la tabla padre, los valores correspondientes en la clave foránea de la tabla hija se actualizan automáticamente para coincidir. (Útil si las PKs pueden cambiar, aunque esto se debe evitar).

    ¡Cuidado con CASCADE! Puede llevar a eliminaciones masivas de datos si no se entiende bien la estructura de relaciones.

  • SET NULL:
    • ON DELETE SET NULL: Si se elimina una fila en la tabla padre, los valores de la clave foránea en las filas relacionadas de la tabla hija se establecen a NULL. Esto solo es posible si la columna de la clave foránea en la tabla hija permite valores NULL.
    • ON UPDATE SET NULL: Si se actualiza la clave primaria en la tabla padre, los valores de la FK en la tabla hija se establecen a NULL.

    Útil cuando la relación es opcional y no quieres eliminar las filas hijas.

  • SET DEFAULT: No soportado por InnoDB en MySQL. Requeriría que la columna FK tenga un valor DEFAULT definido.

Ejemplo con acciones referenciales:

CREATE TABLE categorias (
    id_categoria INT AUTO_INCREMENT PRIMARY KEY,
    nombre_categoria VARCHAR(50) NOT NULL UNIQUE
);

CREATE TABLE productos (
    id_producto INT AUTO_INCREMENT PRIMARY KEY,
    nombre_producto VARCHAR(100) NOT NULL,
    id_categoria_fk INT,
    precio DECIMAL(10,2),
    CONSTRAINT fk_producto_categoria -- Nombre de la restricción
        FOREIGN KEY (id_categoria_fk) REFERENCES categorias(id_categoria)
        ON DELETE SET NULL  -- Si se borra una categoría, los productos de esa categoría tendrán id_categoria_fk = NULL
        ON UPDATE CASCADE;  -- Si se actualiza id_categoria en 'categorias', se actualiza aquí (raro)
);

La elección de la acción referencial correcta depende de la lógica de negocio de tu aplicación.

3.2.1. INNER JOIN

El INNER JOIN (o simplemente JOIN, ya que INNER es el tipo de join por defecto si no se especifica) devuelve solo las filas que tienen una coincidencia en ambas tablas según la condición de unión especificada en la cláusula ON.

Sintaxis:

SELECT T1.columna1, T1.columna2, T2.columnaA, T2.columnaB
FROM tabla1 T1
INNER JOIN tabla2 T2 ON T1.columna_comun = T2.columna_comun;

(T1 y T2 son alias de tabla, muy recomendables en joins para abreviar y evitar ambigüedad).

Ejemplo: Obtener los nombres de los clientes y las fechas de sus pedidos.

Solo se mostrarán clientes que tengan pedidos, y pedidos que tengan un cliente asociado.

SELECT
    c.nombre AS nombre_cliente,
    p.id_pedido,
    p.fecha_pedido
FROM clientes c
INNER JOIN pedidos p ON c.id_cliente = p.id_cliente_fk;

Si un cliente no tiene pedidos, no aparecerá. Si un pedido tiene un id_cliente_fk que no existe en clientes (o es NULL), ese pedido no aparecerá.

[Volver al Índice Principal]

3.2.2. LEFT JOIN (o LEFT OUTER JOIN)

El LEFT JOIN (o LEFT OUTER JOIN, la palabra OUTER es opcional) devuelve todas las filas de la tabla izquierda (la que aparece antes del LEFT JOIN) y las filas coincidentes de la tabla derecha. Si no hay una coincidencia en la tabla derecha, se devuelven valores NULL para todas las columnas de la tabla derecha.

Sintaxis:

SELECT T1.columna1, T1.columna2, T2.columnaA, T2.columnaB
FROM tabla1 T1 -- Tabla izquierda
LEFT JOIN tabla2 T2 ON T1.columna_comun = T2.columna_comun;

Ejemplo: Obtener todos los clientes y las fechas de sus pedidos, incluso si un cliente no tiene pedidos.

SELECT
    c.nombre AS nombre_cliente,
    p.id_pedido,
    p.fecha_pedido
FROM clientes c -- Tabla izquierda
LEFT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk;

Si el "Cliente C" no tiene pedidos, aparecerá en el resultado, pero p.id_pedido y p.fecha_pedido serán NULL para él.

Caso de uso: Encontrar filas en la tabla izquierda que no tienen correspondencia en la tabla derecha.

Ejemplo: Clientes que no han realizado ningún pedido.

SELECT c.nombre
FROM clientes c
LEFT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk
WHERE p.id_pedido IS NULL; -- Donde no hubo coincidencia en la tabla derecha (pedidos)

[Volver al Índice Principal]

3.2.3. RIGHT JOIN (o RIGHT OUTER JOIN)

El RIGHT JOIN (o RIGHT OUTER JOIN) es lo opuesto al LEFT JOIN. Devuelve todas las filas de la tabla derecha (la que aparece después del RIGHT JOIN) y las filas coincidentes de la tabla izquierda. Si no hay una coincidencia en la tabla izquierda, se devuelven valores NULL para todas las columnas de la tabla izquierda.

Sintaxis:

SELECT T1.columna1, T1.columna2, T2.columnaA, T2.columnaB
FROM tabla1 T1
RIGHT JOIN tabla2 T2 ON T1.columna_comun = T2.columna_comun; -- Tabla derecha

Ejemplo: Obtener todos los pedidos y los nombres de sus clientes, incluso si un pedido no tiene un cliente asociado (o el cliente_id es NULL o no válido).

SELECT
    c.nombre AS nombre_cliente,
    p.id_pedido,
    p.fecha_pedido
FROM clientes c
RIGHT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk; -- Tabla derecha

Si el pedido con id_pedido = 104 tiene un id_cliente_fk que no existe en clientes (o es NULL), este pedido aparecerá, pero c.nombre será NULL para él.

Muchos desarrolladores prefieren usar LEFT JOIN y simplemente invertir el orden de las tablas en la cláusula FROM para lograr el mismo resultado que un RIGHT JOIN, ya que LEFT JOIN suele ser más intuitivo para leer.

3.2.4. FULL OUTER JOIN (Simulación en MySQL)

El FULL OUTER JOIN (o FULL JOIN) devuelve todas las filas cuando hay una coincidencia en la tabla izquierda O en la tabla derecha. Es decir, incluye todas las filas de ambas tablas. Si no hay coincidencia para una fila de una tabla, las columnas de la otra tabla tendrán valores NULL.

MySQL no soporta directamente la sintaxis FULL OUTER JOIN.

Se puede simular usando una combinación de LEFT JOIN, UNION ALL (o UNION), y RIGHT JOIN (donde la parte del RIGHT JOIN excluye las filas ya cubiertas por el LEFT JOIN).

Simulación Común:

(SELECT
    c.id_cliente,
    c.nombre AS nombre_cliente,
    p.id_pedido,
    p.fecha_pedido
FROM clientes c
LEFT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk)
UNION -- UNION elimina duplicados, UNION ALL los incluye. Para FULL JOIN, UNION es a menudo lo correcto.
(SELECT
    c.id_cliente,
    c.nombre AS nombre_cliente,
    p.id_pedido,
    p.fecha_pedido
FROM clientes c
RIGHT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk
WHERE c.id_cliente IS NULL); -- Solo los pedidos que no tuvieron un cliente en el LEFT JOIN

Esta consulta mostrará todos los clientes (con sus pedidos si los tienen, o NULLs si no) Y todos los pedidos (con sus clientes si los tienen, o NULLs si no).

3.2.5. SELF JOIN

Un SELF JOIN es un join regular, pero la tabla se une consigo misma. Para hacer esto, se deben usar alias de tabla para tratar las dos instancias de la misma tabla como si fueran tablas diferentes.

Es útil para consultar datos jerárquicos o relaciones dentro de la misma tabla.

Ejemplo: Tabla de empleados con una columna `jefe_id` que referencia al `id_empleado` del jefe.

CREATE TABLE IF NOT EXISTS empleados_con_jefe (
    id_empleado INT PRIMARY KEY,
    nombre_empleado VARCHAR(100),
    jefe_id INT,
    FOREIGN KEY (jefe_id) REFERENCES empleados_con_jefe(id_empleado) ON DELETE SET NULL -- Un empleado puede no tener jefe (ej. el CEO)
);

-- INSERT INTO empleados_con_jefe VALUES (1, 'CEO Laura', NULL), (2, 'Manager Pedro', 1), (3, 'Empleado Ana', 2), (4, 'Empleado Juan', 2);

Consulta para obtener el nombre de cada empleado y el nombre de su jefe:

SELECT
    e.nombre_empleado AS Empleado,
    j.nombre_empleado AS Jefe
FROM empleados_con_jefe e -- Alias 'e' para la instancia del empleado
LEFT JOIN empleados_con_jefe j ON e.jefe_id = j.id_empleado; -- Alias 'j' para la instancia del jefe

Se usa LEFT JOIN para incluir también a los empleados que no tienen jefe (como el CEO, cuyo jefe_id sería NULL).

3.2.6. Uso de Alias en Tablas y Columnas

Como ya se ha visto en los ejemplos anteriores, el uso de alias es fundamental cuando se trabaja con JOINs (y también útil en consultas más simples).

Alias de Tabla:

  • Se definen en la cláusula FROM o JOIN después del nombre de la tabla (la palabra clave AS es opcional).
  • Propósitos:
    • Abreviar nombres de tabla largos: Hace la consulta más corta y legible.
    • Resolver ambigüedad: Si unes dos tablas que tienen columnas con el mismo nombre (ej. ambas tablas tienen una columna id), debes prefijar el nombre de la columna con el alias de la tabla para especificar de cuál tabla quieres la columna (ej. c.id, p.id).
    • Necesario en SELF JOINs: Para distinguir entre las diferentes "instancias" de la misma tabla.

Alias de Columna:

  • Se definen en la lista SELECT después del nombre de la columna o expresión, usando AS nombre_alias (AS es opcional pero recomendado).
  • Propósitos:
    • Hacer los encabezados de los resultados más descriptivos.
    • Renombrar columnas resultantes de expresiones o funciones (ej. COUNT(*) AS total_filas).
    • Evitar conflictos de nombres si una aplicación cliente espera nombres específicos.

Ejemplo Combinado:

SELECT
    c.nombre AS Cliente,
    p.id_pedido AS NumeroPedido,
    pr.nombre_producto AS Producto,
    dp.cantidad AS Unidades
FROM clientes c
JOIN pedidos p ON c.id_cliente = p.id_cliente_fk
JOIN detalle_pedidos dp ON p.id_pedido = dp.id_pedido_fk
JOIN productos pr ON dp.id_producto_fk = pr.id_producto
WHERE c.nombre LIKE 'Cliente A%';

El uso consistente de alias mejora significativamente la legibilidad y mantenibilidad de las consultas SQL complejas.

3.3. Subconsultas (Subqueries)

Una subconsulta o subquery es una consulta SQL anidada dentro de otra consulta SQL. La subconsulta se ejecuta primero, y su resultado es utilizado por la consulta externa (o principal).

Las subconsultas pueden aparecer en varias partes de una sentencia SQL: en la cláusula SELECT, FROM, WHERE, o HAVING.

[Volver al Índice Principal]

3.3.1. Subconsultas en la Cláusula WHERE

Son las más comunes. Se utilizan para filtrar los resultados de la consulta principal basándose en el resultado de la subconsulta.

  • Subconsultas Escalares (devuelven un solo valor: una fila, una columna):

    Se pueden usar con operadores de comparación (=, <, >, etc.).

    Ejemplo: Encontrar productos cuyo precio sea mayor que el precio promedio de todos los productos.

    SELECT nombre_producto, precio
FROM productos
WHERE precio > (SELECT AVG(precio) FROM productos);
  • Subconsultas que devuelven una lista de valores (una columna, múltiples filas):

    Se usan con operadores como IN, NOT IN, ANY, ALL.

    Ejemplo: Encontrar clientes que han realizado al menos un pedido.

    SELECT nombre
FROM clientes
WHERE id_cliente IN (SELECT DISTINCT id_cliente_fk FROM pedidos WHERE id_cliente_fk IS NOT NULL);
  • Subconsultas Correlacionadas:

    Una subconsulta correlacionada es aquella que depende de la consulta externa para sus valores. Se ejecuta una vez por cada fila procesada por la consulta externa. Pueden ser menos eficientes si no se usan con cuidado.

    Ejemplo: Encontrar todos los pedidos cuyo total sea mayor que el total promedio de los pedidos de ese mismo cliente.

    -- Suponiendo que pedidos tiene 'total_pedido'
SELECT p1.id_pedido, p1.id_cliente_fk, p1.total_pedido
FROM pedidos p1
WHERE p1.total_pedido > (
    SELECT AVG(p2.total_pedido)
    FROM pedidos p2
    WHERE p2.id_cliente_fk = p1.id_cliente_fk -- Correlación con la consulta externa
);

[Volver al Índice Principal]

3.3.2. Subconsultas en la Cláusula SELECT

Una subconsulta en la lista SELECT debe ser una subconsulta escalar (devolver un único valor). Se ejecuta para cada fila devuelta por la consulta principal.

Ejemplo: Mostrar el nombre de cada cliente y el número total de pedidos que ha realizado.

SELECT
    c.nombre AS nombre_cliente,
    (
        SELECT COUNT(*)
        FROM pedidos p
        WHERE p.id_cliente_fk = c.id_cliente -- Subconsulta correlacionada
    ) AS numero_total_pedidos
FROM clientes c;

Aunque esto funciona, a menudo un JOIN con GROUP BY puede ser más eficiente para este tipo de cálculo:

SELECT c.nombre AS nombre_cliente, COUNT(p.id_pedido) AS numero_total_pedidos
FROM clientes c
LEFT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk
GROUP BY c.id_cliente, c.nombre;

[Volver al Índice Principal]

3.3.3. Subconsultas en la Cláusula FROM (Tablas Derivadas)

Cuando una subconsulta se usa en la cláusula FROM, su conjunto de resultados se trata como una tabla temporal, conocida como tabla derivada. Esta tabla derivada debe tener un alias.

Ejemplo: Obtener el promedio de los totales de pedidos para cada cliente, y luego mostrar solo los clientes cuyo promedio de pedido es mayor a un cierto valor.

SELECT
    cliente_info.nombre_cliente,
    cliente_info.promedio_total_pedido
FROM (
    -- Subconsulta: Calcula el promedio del total de pedido por cliente
    SELECT
        c.nombre AS nombre_cliente,
        AVG(p.total_pedido) AS promedio_total_pedido -- Suponiendo que pedidos tiene 'total_pedido'
    FROM clientes c
    JOIN pedidos p ON c.id_cliente = p.id_cliente_fk
    GROUP BY c.id_cliente, c.nombre
) AS cliente_info -- Alias para la tabla derivada
WHERE cliente_info.promedio_total_pedido > 100.00;

Las tablas derivadas son útiles para realizar cálculos intermedios o para simplificar consultas complejas dividiéndolas en pasos lógicos.

[Volver al Índice Principal]

3.3.4. Operadores EXISTS y NOT EXISTS

El operador EXISTS se utiliza en la cláusula WHERE para comprobar si una subconsulta devuelve alguna fila. Devuelve TRUE si la subconsulta produce una o más filas, y FALSE si no produce ninguna. NOT EXISTS es lo contrario.

EXISTS es a menudo más eficiente que IN o JOIN para ciertas comprobaciones de existencia, ya que la subconsulta puede detenerse tan pronto como encuentra la primera fila que cumple la condición.

Ejemplo: Encontrar clientes que han realizado al menos un pedido (usando EXISTS).

SELECT c.nombre
FROM clientes c
WHERE EXISTS (
    SELECT 1 -- El contenido del SELECT no importa, solo si devuelve filas
    FROM pedidos p
    WHERE p.id_cliente_fk = c.id_cliente -- Subconsulta correlacionada
);

Ejemplo: Encontrar clientes que NO han realizado ningún pedido (usando NOT EXISTS).

SELECT c.nombre
FROM clientes c
WHERE NOT EXISTS (
    SELECT 1
    FROM pedidos p
    WHERE p.id_cliente_fk = c.id_cliente
);

EXISTS es particularmente útil con subconsultas correlacionadas.

3.4. Vistas (Views)

[Volver al Índice Principal]

3.4.1. ¿Qué son las Vistas y para qué sirven?

Una vista (View) es una tabla virtual cuyo contenido está definido por una consulta SQL. Una vista no almacena datos por sí misma (generalmente, aunque hay vistas materializadas en algunos SGBD, no es el caso estándar en MySQL Community). En cambio, cada vez que se consulta una vista, la consulta subyacente que la define se ejecuta para generar los resultados.

Propósitos y Ventajas de las Vistas:

  • Simplificación de Consultas Complejas: Si tienes una consulta SELECT larga y compleja que usas frecuentemente (por ejemplo, una que involucra múltiples JOINs y cálculos), puedes guardarla como una vista y luego consultarla como si fuera una tabla simple.
  • Encapsulación de Lógica: Permiten ocultar la complejidad de las tablas subyacentes y la lógica de unión. Los usuarios pueden interactuar con la vista sin necesitar conocer los detalles de la estructura interna.
  • Seguridad: Se pueden usar para restringir el acceso a ciertos datos. Por ejemplo, puedes crear una vista que solo muestre ciertas columnas de una tabla o ciertas filas que cumplen una condición, y luego conceder permisos a los usuarios sobre la vista en lugar de sobre la tabla base.
  • Consistencia de Datos: Ayudan a presentar los datos de una manera consistente a diferentes usuarios o aplicaciones, incluso si la estructura de las tablas subyacentes cambia (siempre que la vista se pueda seguir derivando).
  • Independencia Lógica de Datos: Las aplicaciones pueden basarse en vistas. Si la estructura de las tablas base cambia, solo necesitas modificar la definición de la vista (si es posible) sin cambiar el código de la aplicación que usa la vista.

Una vista se comporta como una tabla en las operaciones de consulta (SELECT). Las operaciones de modificación (INSERT, UPDATE, DELETE) sobre vistas son posibles solo bajo ciertas condiciones (por ejemplo, si la vista no involucra agregaciones, DISTINCT, GROUP BY, UNION, y se basa en una única tabla o es "actualizable").

[Volver al Índice Principal]

3.4.2. CREATE VIEW

El comando CREATE VIEW se utiliza para crear una nueva vista.

Sintaxis:

CREATE [OR REPLACE] VIEW nombre_de_la_vista
[(columna1_vista, columna2_vista, ...)] -- Nombres opcionales para las columnas de la vista
AS
    sentencia_select_que_define_la_vista;
  • OR REPLACE: Si se especifica, y la vista ya existe, será reemplazada por la nueva definición. Si no se especifica y la vista existe, se producirá un error.
  • (columna1_vista, ...): Opcionalmente, puedes especificar los nombres de las columnas para la vista. Si no se especifican, se tomarán de la lista SELECT de la consulta subyacente.
  • AS sentencia_select_que_define_la_vista: La consulta SELECT que define los datos que mostrará la vista.

Ejemplo: Crear una vista que muestre los nombres de los clientes y el total de pedidos que han realizado.

CREATE OR REPLACE VIEW vista_clientes_con_total_pedidos AS
SELECT
    c.nombre AS nombre_cliente,
    COUNT(p.id_pedido) AS total_pedidos_realizados
FROM clientes c
LEFT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk
GROUP BY c.id_cliente, c.nombre;

Cómo usar la vista:

Una vez creada, puedes consultarla como si fuera una tabla:

SELECT * FROM vista_clientes_con_total_pedidos
WHERE total_pedidos_realizados > 1
ORDER BY nombre_cliente;

3.4.3. ALTER VIEW y DROP VIEW

ALTER VIEW:

El comando ALTER VIEW se utiliza para modificar la definición de una vista existente.

Sintaxis:

ALTER VIEW nombre_de_la_vista
[(columna1_vista, columna2_vista, ...)]
AS
    nueva_sentencia_select;

Es funcionalmente equivalente a usar CREATE OR REPLACE VIEW.

Ejemplo: Modificar la vista anterior para incluir el email del cliente.

ALTER VIEW vista_clientes_con_total_pedidos AS
SELECT
    c.nombre AS nombre_cliente,
    c.email AS email_cliente,
    COUNT(p.id_pedido) AS total_pedidos_realizados
FROM clientes c
LEFT JOIN pedidos p ON c.id_cliente = p.id_cliente_fk
GROUP BY c.id_cliente, c.nombre, c.email;

DROP VIEW:

El comando DROP VIEW se utiliza para eliminar una vista existente. No afecta a los datos de las tablas base.

Sintaxis:

DROP VIEW [IF EXISTS] nombre_de_la_vista;
  • IF EXISTS: Evita un error si la vista no existe.

Ejemplo:

DROP VIEW IF EXISTS vista_clientes_con_total_pedidos;

3.5. Índices (Indexes)

[Volver al Índice Principal]

3.5.1. Concepto y Propósito de los Índices

Un índice (index) en una base de datos es una estructura de datos especial, asociada a una tabla, que permite acelerar significativamente las operaciones de recuperación de datos (consultas SELECT que usan condiciones WHERE o cláusulas JOIN y ORDER BY sobre las columnas indexadas).

Imagina el índice de un libro: en lugar de leer todo el libro para encontrar un tema, vas al índice, buscas el tema y te dice en qué página está. De manera similar, un índice de base de datos contiene punteros a las filas de la tabla, organizados de una forma que facilita búsquedas rápidas.

Propósitos de los Índices:

  • Mejorar el rendimiento de las consultas: Es su principal objetivo. Reducen la cantidad de datos que el SGBD necesita escanear para encontrar las filas deseadas.
  • Asegurar la unicidad: Los índices únicos (UNIQUE INDEX) y las claves primarias (que implícitamente crean un índice único) garantizan que no haya valores duplicados en las columnas indexadas.
  • Facilitar la ordenación: Si una columna está indexada, ordenar por esa columna puede ser más rápido.

Desventajas de los Índices:

  • Espacio en Disco: Los índices ocupan espacio adicional en disco.
  • Rendimiento en Operaciones de Escritura: Cuando se insertan, actualizan o eliminan filas, los índices asociados también deben actualizarse, lo que puede ralentizar estas operaciones (INSERT, UPDATE, DELETE).

Por lo tanto, es un equilibrio: se deben crear índices en las columnas que se consultan con frecuencia, pero no en todas las columnas indiscriminadamente.

[Volver al Índice Principal]

3.5.2. Tipos de Índices (PRIMARY, UNIQUE, INDEX)

MySQL soporta varios tipos de índices:

  • PRIMARY KEY (Índice de Clave Primaria):

    Cada tabla puede tener como máximo una clave primaria. La clave primaria identifica unívocamente cada fila. En MySQL, cuando defines una PRIMARY KEY, se crea automáticamente un índice único para ella. Los valores de la clave primaria no pueden ser NULL.

  • UNIQUE INDEX (Índice Único):

    Asegura que todos los valores en la columna (o combinación de columnas) indexada sean únicos. A diferencia de la clave primaria, una tabla puede tener múltiples índices únicos. Un índice único permite valores NULL (y múltiples NULLs, ya que NULL no es igual a NULL en términos de unicidad de índice, a menos que la columna también sea NOT NULL).

    Se crea con la restricción UNIQUE al definir la tabla o con CREATE UNIQUE INDEX.

  • INDEX (Índice Regular o No Único):

    Este es el tipo de índice estándar. Permite valores duplicados en la columna indexada. Su propósito principal es acelerar las búsquedas.

    Se crea con CREATE INDEX o especificando KEY o INDEX en la definición de la tabla.

  • FULLTEXT INDEX (Índice de Texto Completo):

    Diseñado para realizar búsquedas de texto completo en columnas de tipo CHAR, VARCHAR o TEXT. Permite búsquedas por palabras o frases, ignorando palabras comunes (stop words) y utilizando algoritmos de relevancia. Se usa con las funciones MATCH() ... AGAINST().

  • Índices Compuestos (Multi-columna):

    Un índice puede crearse sobre múltiples columnas. El orden de las columnas en un índice compuesto es importante. Por ejemplo, un índice en (apellido, nombre) es diferente a un índice en (nombre, apellido). Son útiles cuando las consultas filtran u ordenan por varias columnas simultáneamente.

  • Índices Espaciales: Para tipos de datos espaciales.

La elección del tipo de índice depende de los requisitos de unicidad y los patrones de consulta.

[Volver al Índice Principal]

3.5.3. CREATE INDEX y DROP INDEX

Aunque los índices se pueden crear implícitamente con restricciones PRIMARY KEY y UNIQUE en la definición de la tabla, también se pueden añadir o eliminar explícitamente.

CREATE INDEX:

Para crear un índice regular (no único) o único después de que la tabla ha sido creada.

Sintaxis:

CREATE [UNIQUE | FULLTEXT | SPATIAL] INDEX nombre_del_indice
ON nombre_de_la_tabla (columna1 [ASC|DESC], columna2 [ASC|DESC], ...);
  • UNIQUE | FULLTEXT | SPATIAL: Opcional, para especificar el tipo de índice. Si se omite, se crea un índice regular.
  • nombre_del_indice: Un nombre para el índice. Debe ser único dentro de la tabla.
  • nombre_de_la_tabla: La tabla a la que pertenece el índice.
  • (columna1, ...): Las columnas que formarán parte del índice. Para índices espaciales, solo se puede indexar una columna.
  • ASC | DESC: Opcional (MySQL 8.0+ para InnoDB), especifica el orden de almacenamiento para el índice, útil para optimizar ciertas consultas ORDER BY.

Ejemplo: Crear un índice en la columna `email` de la tabla `estudiantes`.

CREATE INDEX idx_estudiantes_email ON estudiantes (email);

Ejemplo: Crear un índice único en `titulo` y `autor_id` en la tabla `libros`.

CREATE UNIQUE INDEX uq_libros_titulo_autor ON libros (titulo, autor_id);

DROP INDEX:

Para eliminar un índice existente.

Sintaxis:

DROP INDEX nombre_del_indice ON nombre_de_la_tabla;

Ejemplo: Eliminar el índice `idx_estudiantes_email`.

DROP INDEX idx_estudiantes_email ON estudiantes;

No se puede usar DROP INDEX para eliminar una clave primaria. Para ello, se usa ALTER TABLE nombre_tabla DROP PRIMARY KEY;.

Para ver los índices de una tabla, puedes usar:

SHOW INDEX FROM nombre_de_la_tabla;

3.5.4. Consideraciones de Rendimiento

La correcta utilización de índices es crucial para el rendimiento de una base de datos.

Cuándo crear índices:

  • Columnas en cláusulas WHERE: Las columnas que se usan frecuentemente para filtrar datos son candidatas principales para indexación.
  • Columnas en cláusulas JOIN: Las columnas usadas en las condiciones ON de los joins (generalmente claves primarias y foráneas) deben estar indexadas. MySQL suele crear índices para las FKs automáticamente si el motor lo soporta (como InnoDB).
  • Columnas en cláusulas ORDER BY y GROUP BY: Indexar estas columnas puede evitar costosas operaciones de ordenación o agrupación en archivos temporales.
  • Columnas con alta cardinalidad: La cardinalidad se refiere al número de valores únicos en una columna en relación con el número total de filas. Los índices son más efectivos en columnas con alta cardinalidad (muchos valores diferentes, como un ID o un email). Son menos efectivos en columnas con baja cardinalidad (pocos valores diferentes, como un campo de "género" con solo 'M' o 'F').

Qué NO indexar (o hacerlo con cuidado):

  • Todas las columnas: Esto degradaría el rendimiento de las escrituras y ocuparía mucho espacio.
  • Columnas que raramente se usan en consultas.
  • Columnas con muy baja cardinalidad (a menos que las consultas específicas se beneficien mucho de ello).
  • Tablas muy pequeñas: El SGBD puede escanear la tabla completa más rápido que usar un índice.
  • Columnas de tipo TEXT o BLOB largas: Se pueden indexar los primeros N caracteres (índices de prefijo) si es necesario, pero indexar la columna completa puede ser ineficiente. Para búsquedas en este tipo de columnas, se suelen usar índices FULLTEXT.

Uso de EXPLAIN:

MySQL proporciona el comando EXPLAIN (o EXPLAIN ANALYZE en versiones más recientes) que muestra cómo el optimizador de MySQL planea ejecutar una consulta SELECT. Es una herramienta invaluable para entender si se están utilizando los índices, qué tipo de join se está realizando, cuántas filas se estima que se examinarán, etc.

EXPLAIN SELECT * FROM estudiantes WHERE email = 'ana.perez@example.com';

Analizar la salida de EXPLAIN te ayuda a identificar consultas lentas y a determinar si la adición o modificación de un índice podría mejorar el rendimiento.

El mantenimiento de índices (reconstrucción, análisis) también puede ser necesario periódicamente, aunque los motores modernos como InnoDB suelen manejar esto bien.

El Lenguaje de Control de Transacciones (TCL) se utiliza para gestionar las transacciones dentro de la base de datos.

3.6.1. Concepto de Transacción (ACID)

Una transacción es una secuencia de una o más operaciones SQL (generalmente DML como INSERT, UPDATE, DELETE) que se ejecutan como una única unidad de trabajo lógica e indivisible. Esto significa que, o bien todas las operaciones dentro de la transacción se completan con éxito y sus cambios se hacen permanentes en la base de datos, o bien si alguna operación falla, ninguna de las operaciones de la transacción se aplica y la base de datos se revierte a su estado anterior al inicio de la transacción.

Las transacciones son cruciales para mantener la consistencia e integridad de los datos, especialmente en entornos multiusuario donde pueden ocurrir fallos o accesos concurrentes.

Las transacciones se caracterizan por las propiedades ACID:

  • A - Atomicidad (Atomicity):

    Una transacción es "todo o nada". Si alguna parte de la transacción falla, toda la transacción se deshace (rollback). Si todas las partes tienen éxito, la transacción se confirma (commit) y todos los cambios son permanentes.

  • C - Consistencia (Consistency):

    Una transacción debe llevar la base de datos de un estado válido a otro estado válido. Todas las reglas de integridad definidas (claves primarias, foráneas, restricciones CHECK, etc.) deben cumplirse al final de la transacción. Si una transacción viola estas reglas, se revierte.

  • I - Aislamiento (Isolation):

    Las transacciones concurrentes (que se ejecutan al mismo tiempo) deben estar aisladas unas de otras. Los resultados de una transacción no finalizada no deben ser visibles para otras transacciones hasta que la primera se complete. Esto previene problemas como lecturas sucias, lecturas no repetibles y lecturas fantasma. Los SGBD ofrecen diferentes niveles de aislamiento transaccional.

  • D - Durabilidad (Durability):

    Una vez que una transacción ha sido confirmada (COMMIT), sus cambios son permanentes y deben sobrevivir a fallos posteriores del sistema (como un reinicio del servidor o un fallo de energía). Esto se logra típicamente mediante el uso de logs de transacciones.

En MySQL, el motor de almacenamiento InnoDB es el que proporciona soporte completo para transacciones ACID. MyISAM, el antiguo motor por defecto, no soporta transacciones.

Por defecto, MySQL opera en modo autocommit=ON. Esto significa que cada sentencia SQL individual se trata como una transacción separada y se confirma automáticamente si tiene éxito. Para realizar transacciones de múltiples sentencias, necesitas desactivar autocommit o iniciar explícitamente una transacción.

[Volver al Índice Principal]

3.6.2. START TRANSACTION

El comando START TRANSACTION (o sus sinónimos BEGIN o BEGIN WORK) se utiliza para iniciar explícitamente una nueva transacción. Cuando inicias una transacción, el modo autocommit se desactiva temporalmente para la sesión actual hasta que la transacción se complete con un COMMIT o un ROLLBACK.

Sintaxis:

START TRANSACTION;

Opcionalmente, se pueden especificar características de la transacción:

START TRANSACTION READ WRITE; -- Predeterminado
START TRANSACTION READ ONLY;
START TRANSACTION WITH CONSISTENT SNAPSHOT; -- Para ciertos niveles de aislamiento

Ejemplo:

START TRANSACTION;
-- A partir de aquí, las siguientes operaciones DML forman parte de la misma transacción
UPDATE cuentas SET saldo = saldo - 100 WHERE id_cuenta = 1;
UPDATE cuentas SET saldo = saldo + 100 WHERE id_cuenta = 2;
-- Los cambios aún no son permanentes ni visibles para otras sesiones.

También puedes desactivar autocommit para la sesión actual con:

SET autocommit = 0;

Después de esto, cada grupo de sentencias DML requerirá un COMMIT o ROLLBACK explícito.

[Volver al Índice Principal]

3.6.3. COMMIT

El comando COMMIT (o COMMIT WORK) finaliza la transacción actual y hace permanentes todos los cambios realizados desde el inicio de la transacción (o el último COMMIT/ROLLBACK).

Sintaxis:

COMMIT;

Ejemplo (continuando el anterior):

START TRANSACTION;
UPDATE cuentas SET saldo = saldo - 100 WHERE id_cuenta = 1;
UPDATE cuentas SET saldo = saldo + 100 WHERE id_cuenta = 2;
COMMIT; -- Ahora los cambios son permanentes y visibles para otras transacciones.

Después de un COMMIT (o ROLLBACK), si autocommit sigue desactivado (SET autocommit = 0;), se inicia automáticamente una nueva transacción. Si autocommit está activado (por defecto o si se usó START TRANSACTION), la sesión vuelve al modo autocommit.

[Volver al Índice Principal]

3.6.4. ROLLBACK

El comando ROLLBACK (o ROLLBACK WORK) deshace todos los cambios realizados en la transacción actual desde su inicio (o el último COMMIT/ROLLBACK o SAVEPOINT). La base de datos vuelve al estado en que se encontraba antes de que comenzara la transacción (o el savepoint).

Se utiliza cuando ocurre un error durante la transacción o si se decide no completar los cambios.

Sintaxis:

ROLLBACK;

Ejemplo:

START TRANSACTION;
UPDATE cuentas SET saldo = saldo - 100 WHERE id_cuenta = 1;
-- Imaginemos que la siguiente operación falla o se detecta un problema
UPDATE cuentas SET saldo = saldo + 100 WHERE id_cuenta = 999; -- Supongamos que la cuenta 999 no existe y esto causa un error

-- Si hubo un error o se decide no continuar:
ROLLBACK; -- El primer UPDATE (saldo - 100) también se deshace. La BD queda como estaba antes del START TRANSACTION.

[Volver al Índice Principal]

3.6.5. SAVEPOINT

Un SAVEPOINT permite establecer puntos de guardado intermedios dentro de una transacción más larga. Si ocurre un error o se necesita deshacer solo una parte de la transacción, se puede hacer un ROLLBACK TO SAVEPOINT nombre_del_savepoint para revertir los cambios hasta ese punto, sin deshacer toda la transacción.

Sintaxis para crear un savepoint:

SAVEPOINT nombre_del_savepoint;

Sintaxis para revertir a un savepoint:

ROLLBACK TO SAVEPOINT nombre_del_savepoint;

Sintaxis para liberar un savepoint (opcional, se liberan al hacer COMMIT o ROLLBACK completo):

RELEASE SAVEPOINT nombre_del_savepoint;

Ejemplo:

START TRANSACTION;

-- Operación 1
INSERT INTO tabla_A (col1) VALUES ('valorA');
SAVEPOINT sp1;

-- Operación 2
INSERT INTO tabla_B (col2) VALUES ('valorB');
-- Supongamos que aquí ocurre un error o se decide deshacer solo la Operación 2
ROLLBACK TO SAVEPOINT sp1; -- Deshace la inserción en tabla_B, pero la inserción en tabla_A permanece (dentro de la transacción)

-- Operación 3 (se ejecuta después de volver a sp1)
INSERT INTO tabla_C (col3) VALUES ('valorC');

COMMIT; -- Confirma la inserción en tabla_A y tabla_C. La inserción en tabla_B no se aplicó.

Si se hace un ROLLBACK completo (sin TO SAVEPOINT), todos los savepoints se descartan y toda la transacción se revierte.

El uso adecuado de transacciones es esencial para construir aplicaciones de base de datos fiables y consistentes.

4.1.2. Python DB API Specification v2.0

La Python Database API Specification v2.0 (PEP 249) es una especificación que define una interfaz estándar para los módulos de Python que acceden a bases de datos. El objetivo principal de esta especificación es promover la consistencia entre los diferentes adaptadores de bases de datos disponibles para Python, facilitando así la escritura de código portable que pueda interactuar con diferentes sistemas de bases de datos con cambios mínimos.

La DB-API v2.0 define:

  • Módulos Requeridos: Cómo se debe importar el módulo y las variables globales que debe exponer (como apilevel, threadsafety, paramstyle).
  • Objetos de Conexión (Connection Objects):
    • Método connect() para establecer una conexión con la base de datos.
    • Métodos como close(), commit(), rollback().
    • Método cursor() para crear un objeto cursor.
  • Objetos Cursor (Cursor Objects):
    • Método execute(operation, [parameters]) para ejecutar sentencias SQL.
    • Método executemany(operation, seq_of_parameters) para ejecutar una sentencia SQL múltiples veces con diferentes conjuntos de parámetros.
    • Métodos para recuperar resultados (fetching): fetchone(), fetchall(), fetchmany([size]).
    • Atributos como description (información sobre las columnas del resultado), rowcount (número de filas afectadas por la última operación).
    • Método close().
  • Manejo de Errores y Excepciones: Una jerarquía de excepciones estándar (ej. Error, Warning, InterfaceError, DatabaseError, IntegrityError, ProgrammingError).
  • Tipos de Datos: Constructores y constantes para representar tipos de datos de la base de datos en Python.
  • Parámetros de Estilo (paramstyle): Especifica cómo se deben pasar los parámetros a las consultas (ej. qmark para ?, format o pyformat para %s o %(name)s).

La mayoría de los conectores de bases de datos para Python, incluido mysql-connector-python (el conector oficial de MySQL), se esfuerzan por cumplir con esta especificación. Esto significa que, si aprendes a usar un conector que sigue la DB-API, gran parte de ese conocimiento será transferible si necesitas trabajar con otra base de datos (por ejemplo, PostgreSQL con psycopg2 o SQLite con el módulo sqlite3 incorporado en Python).

4.3.2. El objeto Conexión: connect()

La función principal para establecer una conexión es mysql.connector.connect(). Esta función devuelve un objeto de Conexión (Connection Object) si la conexión es exitosa, o lanza una excepción de tipo Error (o una subclase) si falla.

[Volver al Índice Principal]

4.3.2.1. Parámetros de Conexión (host, user, password, database)

La función connect() acepta varios argumentos como palabra clave (keyword arguments) para especificar los detalles de la conexión. Los más comunes son:

  • host (string): El nombre del host o la dirección IP del servidor MySQL. Para un servidor local, suele ser 'localhost' o '127.0.0.1'.
  • user (string): El nombre de usuario de MySQL con el que te quieres conectar (ej. 'root' o un usuario específico que hayas creado).
  • password (string): La contraseña para el usuario especificado.
  • database (string, opcional): El nombre de la base de datos a la que te quieres conectar por defecto. Si se omite, te conectarás al servidor pero no a una base de datos específica inicialmente; tendrás que seleccionarla más tarde con USE nombre_bd en una consulta SQL o al crear el cursor.
  • port (int, opcional): El número de puerto en el que el servidor MySQL está escuchando. Por defecto es 3306.
  • Otros parámetros: Hay muchos otros parámetros opcionales para configurar la conexión, como charset, collation, ssl_disabled, connection_timeout, etc.

Ejemplo básico de conexión:

try:
    # Establecer la conexión
    connection = mysql.connector.connect(
        host='localhost',
        user='tu_usuario',      # Reemplaza con tu usuario de MySQL
        password='tu_contraseña', # Reemplaza con tu contraseña
        database='nombre_de_tu_bd' # Reemplaza con el nombre de tu BD, o omite si no quieres conectar a una específica
    )

    if connection.is_connected():
        db_Info = connection.get_server_info()
        print(f"Conectado a MySQL Server versión {db_Info}")
        cursor = connection.cursor()
        cursor.execute("SELECT DATABASE();") # Verifica la base de datos actual
        record = cursor.fetchone()
        print(f"Estás conectado a la base de datos: {record[0] if record else 'Ninguna'}")

except Error as e:
    print(f"Error al conectar a MySQL: {e}")

finally:
    # Asegurarse de cerrar la conexión
    if 'connection' in locals() and connection.is_connected():
        if 'cursor' in locals(): # Asegurarse de que el cursor existe antes de cerrarlo
            cursor.close()
        connection.close()
        print("Conexión a MySQL cerrada.")

¡Importante! Nunca incrustes contraseñas directamente en el código en aplicaciones de producción. Utiliza variables de entorno, archivos de configuración seguros o sistemas de gestión de secretos.

4.3.3. Manejo de Errores de Conexión (try-except)

Como se muestra en el ejemplo anterior, es crucial envolver la llamada a mysql.connector.connect() y las operaciones subsiguientes en un bloque try...except Error as e:.

Esto permite capturar cualquier error que pueda ocurrir durante el proceso de conexión, como:

  • Servidor MySQL no disponible o no accesible (host incorrecto, puerto cerrado, firewall bloqueando).
  • Credenciales de usuario/contraseña incorrectas.
  • La base de datos especificada no existe.
  • Problemas de red.

Al capturar la excepción mysql.connector.Error (o subclases más específicas si es necesario), puedes manejar el error de forma controlada (ej. mostrando un mensaje al usuario, registrando el error) en lugar de que el programa termine abruptamente.

4.3.4. Cerrando la Conexión: close()

Una vez que hayas terminado de trabajar con la base de datos, es fundamental cerrar el objeto de conexión para liberar los recursos que está utilizando tanto en el lado del cliente (Python) como en el servidor MySQL.

El objeto de conexión tiene un método close():

if connection.is_connected():
    connection.close()

El método is_connected() se puede usar para verificar si la conexión sigue activa antes de intentar cerrarla.

El bloque finally en una estructura try...except...finally es el lugar ideal para asegurar que la conexión se cierre, independientemente de si ocurrieron errores o no durante las operaciones de base de datos.

No cerrar las conexiones puede llevar a problemas como:

  • Agotamiento de los límites de conexión en el servidor MySQL.
  • Fugas de memoria en tu aplicación Python.
  • Otros comportamientos inesperados.

4.3.5. Uso del Bloque with para Conexiones y Cursores

En Python, el gestor de contexto with se utiliza comúnmente para asegurar que los recursos se liberen adecuadamente, incluso si ocurren errores. Llama automáticamente a los métodos __enter__() y __exit__() del objeto.

Desafortunadamente, el objeto de conexión devuelto por mysql-connector-python (versiones hasta la 8.0.x al menos) no implementa directamente el protocolo de gestor de contexto. Esto significa que no puedes hacer esto:

# ESTO NO FUNCIONA DIRECTAMENTE CON LA CONEXIÓN DE mysql-connector-python
# with mysql.connector.connect(...) as connection:
#     # ... hacer cosas ...

Sin embargo, el objeto cursor devuelto por connection.cursor() SÍ implementa el protocolo de gestor de contexto. Por lo tanto, la práctica recomendada es usar with para el cursor, y manejar el cierre de la conexión explícitamente en un bloque finally.

connection = None # Inicializar fuera del try para que esté en el scope del finally
try:
    connection = mysql.connector.connect(
        host='localhost', user='tu_usuario', password='tu_contraseña', database='tu_bd'
    )
    if connection.is_connected():
        # Usar 'with' para el cursor asegura que cursor.close() se llame automáticamente
        with connection.cursor() as cursor:
            cursor.execute("SELECT VERSION()")
            version = cursor.fetchone()
            print(f"Versión del servidor MySQL (con with para cursor): {version[0]}")
        
        # Aquí el cursor ya está cerrado
        # connection.commit() # Si hiciste operaciones DML
        
except Error as e:
    print(f"Error: {e}")
    # if connection and connection.is_connected():
    #     connection.rollback() # Si estabas en una transacción
finally:
    if connection and connection.is_connected():
        connection.close()
        print("Conexión cerrada (después de with para cursor).")

Si desearas un gestor de contexto para la conexión en sí misma con `mysql-connector-python`, tendrías que crear una clase wrapper personalizada o utilizar un pool de conexiones que podría ofrecer tal funcionalidad.

4.4. El Objeto Cursor

Una vez que tienes un objeto de conexión, necesitas un objeto cursor para ejecutar sentencias SQL y gestionar los resultados. El cursor actúa como un puntero o manejador para interactuar con el conjunto de resultados de una consulta.

[Volver al Índice Principal]

4.4.1. Creación de un Cursor: connection.cursor()

Se crea un objeto cursor llamando al método cursor() del objeto de conexión.

# Asumiendo que 'connection' es un objeto de conexión válido y activo
try:
    cursor = connection.cursor()
    # Ahora puedes usar 'cursor' para ejecutar consultas
    print("Objeto cursor creado.")
    # ...
except Error as e:
    print(f"Error al crear el cursor: {e}")

Este cursor por defecto suele ser no bufferizado, lo que significa que los resultados se van recuperando del servidor a medida que se solicitan (con fetchone(), fetchall(), etc.).

[Volver al Índice Principal]

4.4.2. Tipos de Cursores (buffered, dictionary)

El método cursor() puede aceptar argumentos para modificar el comportamiento del cursor creado:

  • Cursor Bufferizado (buffered=True): 
    cursor_buffered = connection.cursor(buffered=True)

    Cuando un cursor es bufferizado, todos los resultados de una consulta SELECT se cargan del servidor a la memoria del cliente (en Python) inmediatamente después de ejecutar la consulta. Esto tiene varias implicaciones:

    • Puedes ejecutar otras consultas en la misma conexión antes de haber consumido todos los resultados del cursor bufferizado. Con un cursor no bufferizado, generalmente necesitas procesar todos sus resultados antes de poder ejecutar otra consulta en la misma conexión (o podrías obtener un error "Unread result found").
    • Puedes iterar sobre los resultados múltiples veces si es necesario.
    • Desventaja: Si el conjunto de resultados es muy grande, puede consumir mucha memoria en el cliente.
  • Cursor de Diccionario (dictionary=True): 
    cursor_dict = connection.cursor(dictionary=True)

    En lugar de devolver las filas como tuplas, un cursor de diccionario devuelve cada fila como un diccionario de Python, donde las claves son los nombres de las columnas y los valores son los datos de la fila. Esto puede hacer el código más legible ya que puedes acceder a los campos por su nombre en lugar de por su índice.

    # Con cursor_dict:
# cursor_dict.execute("SELECT id, nombre, email FROM estudiantes WHERE id = 1")
# estudiante = cursor_dict.fetchone()
# if estudiante:
#     print(f"ID: {estudiante['id']}, Nombre: {estudiante['nombre']}")
  • Cursor de Tupla Nombrada (named_tuple=True): 
    cursor_named_tuple = connection.cursor(named_tuple=True)

    Devuelve cada fila como una tupla nombrada. Similar a un diccionario, permite acceder a los campos por nombre (ej. estudiante.nombre), pero también por índice (estudiante[1]), y son más ligeras en memoria que los diccionarios.

Puedes combinar estas opciones, por ejemplo: connection.cursor(buffered=True, dictionary=True).

La elección del tipo de cursor depende de tus necesidades específicas para procesar los resultados y gestionar la memoria.

[Volver al Índice Principal]

4.4.3. Cerrando el Cursor: cursor.close() y uso de with

Al igual que las conexiones, los cursores también deben cerrarse cuando ya no se necesiten para liberar los recursos que puedan estar utilizando.

El objeto cursor tiene un método close():

if 'cursor' in locals() and cursor: # Verificar si la variable existe y no es None
    cursor.close()
    print("Cursor cerrado.")

Uso de with para cursores:

Como se mencionó en la sección 4.3.5, el objeto cursor de mysql-connector-python SÍ implementa el protocolo de gestor de contexto. Esto significa que puedes (y deberías) usar la sentencia with para manejar los cursores. Esto asegura que el método cursor.close() se llame automáticamente al salir del bloque with, incluso si ocurren excepciones dentro del bloque.

Ejemplo con with:

connection = None
try:
    connection = mysql.connector.connect(
        host='localhost', user='tu_usuario', password='tu_contraseña', database='tu_bd'
    )
    if connection.is_connected():
        # El cursor se cerrará automáticamente al salir de este bloque 'with'
        with connection.cursor(dictionary=True) as dict_cursor:
            dict_cursor.execute("SELECT nombre FROM estudiantes WHERE id = 1")
            estudiante = dict_cursor.fetchone()
            if estudiante:
                print(f"Nombre del estudiante (usando with para cursor): {estudiante['nombre']}")
        
        # dict_cursor ya está cerrado aquí

except Error as e:
    print(f"Error con el cursor y with: {e}")
finally:
    if connection and connection.is_connected():
        connection.close()

Usar with para los cursores es la forma más idiomática y segura de manejarlos en Python, ya que reduce la probabilidad de dejar recursos abiertos.

6.1.1. El Peligro de la Concatenación de Cadenas

La inyección SQL es una de las vulnerabilidades de seguridad más comunes y peligrosas en aplicaciones que interactúan con bases de datos. Ocurre cuando datos proporcionados por el usuario (o cualquier fuente no confiable) se incorporan directamente en una sentencia SQL sin una validación o escapado adecuados.

Si construyes tus consultas SQL concatenando cadenas con entradas del usuario, un atacante podría introducir código SQL malicioso que altere la consulta original, permitiéndole:

  • Acceder a datos sensibles a los que no debería tener acceso.
  • Modificar o eliminar datos.
  • Ejecutar comandos administrativos en la base de datos.
  • Incluso, en algunos casos, comprometer el servidor subyacente.

Ejemplo de Vulnerabilidad (¡NO HACER ESTO!):

# ¡VULNERABLE A INYECCIÓN SQL!
# def buscar_usuario_vulnerable(conn, nombre_usuario_input):
#     try:
#         with conn.cursor(dictionary=True) as cursor:
#             # Concatenación directa de la entrada del usuario en la consulta
#             sql_query = "SELECT * FROM usuarios WHERE nombre = '" + nombre_usuario_input + "'"
#             print(f"Ejecutando: {sql_query}") # Para ver la consulta formada
#             cursor.execute(sql_query)
#             resultados = cursor.fetchall()
#             # ... procesar resultados ...
#     except Error as e:
#         print(f"Error: {e}")

# # Un atacante podría proporcionar una entrada como:
# # nombre_malicioso = "Admin' OR '1'='1"
# # La consulta se convertiría en:
# # SELECT * FROM usuarios WHERE nombre = 'Admin' OR '1'='1'
# # ¡Esto devolvería todos los usuarios de la tabla!

# # O peor:
# # nombre_malicioso = "Admin'; DROP TABLE usuarios; --"
# # La consulta se convertiría en:
# # SELECT * FROM usuarios WHERE nombre = 'Admin'; DROP TABLE usuarios; --'
# # ¡Esto podría eliminar la tabla usuarios! (Dependiendo de los permisos y si el SGBD permite múltiples sentencias)

La concatenación directa de cadenas para formar consultas SQL con datos de entrada es extremadamente peligrosa y debe evitarse a toda costa.

6.1.2. Uso de Consultas Parametrizadas (Placeholders)

El estilo de placeholder depende del conector y de su configuración de paramstyle (según la DB-API).

6.2. Manejo de Transacciones en Python

6.2.1. El modo Autocommit

Por defecto, cuando te conectas con mysql-connector-python, el modo autocommit está desactivado (False). Esto es coherente con el comportamiento estándar de la DB-API cuando se trabaja con transacciones.

Significa que después de ejecutar una o más sentencias DML (INSERT, UPDATE, DELETE), debes llamar explícitamente a connection.commit() para que los cambios se hagan permanentes. Si no lo haces y cierras la conexión, o si ocurre un error y llamas a connection.rollback(), los cambios se perderán.

#    # ...
#    connection.autocommit = False # Para volver al modo manual

Para la mayoría de las aplicaciones que requieren integridad, trabajar con autocommit=False y manejar explícitamente commit() y rollback() es la mejor práctica.

6.2.3. Uso de try-except-finally para transacciones seguras

El patrón try...except...finally es esencial para un manejo robusto de transacciones y recursos:

6.3. Gestión de Errores y Excepciones Específicas de MySQL

[Volver al Índice Principal]

6.3.1. Jerarquía de Excepciones del Conector

El módulo mysql.connector.errors (o simplemente mysql.connector ya que las excepciones suelen estar disponibles a través del módulo principal) define una jerarquía de clases de excepción que se adhieren a la Python DB-API v2.0. La clase base principal es mysql.connector.Error.

Algunas excepciones importantes que heredan de Error son:

  • Warning: Para advertencias no fatales.
  • InterfaceError: Errores relacionados con la interfaz del conector en sí, no con la base de datos (ej. uso incorrecto del API).
  • DatabaseError: Clase base para errores relacionados con la base de datos.
    • DataError: Problemas con los datos procesados (ej. división por cero, valor numérico fuera de rango).
    • OperationalError: Errores relacionados con la operación de la base de datos que no están necesariamente bajo el control del programador (ej. error de conexión, servidor no disponible, memoria insuficiente).
    • IntegrityError: Cuando se viola una restricción de integridad de la base de datos (ej. violación de clave foránea, valor duplicado en una columna UNIQUE).
    • InternalError: Errores internos del SGBD (ej. cursor no válido, error de transacción).
    • ProgrammingError: Errores de programación del usuario (ej. tabla no encontrada, error de sintaxis SQL, número incorrecto de parámetros).
    • NotSupportedError: Si se intenta usar una característica no soportada por la base de datos o el conector.

Conocer esta jerarquía te permite capturar tipos de errores más específicos y manejarlos de manera diferente si es necesario.

6.4. Llamada a Procedimientos Almacenados

Los procedimientos almacenados son bloques de código SQL precompilados que se almacenan en la base de datos y se pueden ejecutar por su nombre. Pueden aceptar parámetros de entrada, realizar operaciones complejas y devolver parámetros de salida o conjuntos de resultados.

6.4.1. Creación de un Procedimiento Almacenado simple en MySQL

Primero, creemos un ejemplo de procedimiento almacenado en MySQL. Usaremos el cliente mysql para esto.

Ejemplo: Procedimiento para obtener un estudiante por ID y devolver su nombre como parámetro OUT.

DELIMITER $$ -- Cambiamos el delimitador para poder usar ; dentro del procedimiento

CREATE PROCEDURE obtener_nombre_estudiante_por_id (
    IN p_id_estudiante INT,
    OUT p_nombre_estudiante VARCHAR(100)
)
BEGIN
    SELECT nombre INTO p_nombre_estudiante
    FROM estudiantes
    WHERE id = p_id_estudiante;
END$$

DELIMITER ; -- Restauramos el delimitador estándar

Este procedimiento toma un p_id_estudiante como entrada (IN) y asigna el nombre correspondiente a la variable de salida p_nombre_estudiante (OUT).

6.4.2. El método cursor.callproc()

Desde Python, se utiliza el método cursor.callproc() para ejecutar un procedimiento almacenado.

Sintaxis:

resultado_parametros_out = cursor.callproc(nombre_procedimiento, [lista_de_argumentos])
  • nombre_procedimiento (string): El nombre del procedimiento almacenado a llamar.
  • lista_de_argumentos (lista o tupla, opcional): Una secuencia de argumentos para el procedimiento. El orden debe coincidir con el de los parámetros del procedimiento. Para los parámetros OUT o INOUT, debes pasar un valor inicial (puede ser None o un placeholder como una cadena vacía o 0, dependiendo del tipo esperado por el procedimiento para la variable OUT en la base de datos, aunque el conector lo manejará).
  • resultado_parametros_out: Si el procedimiento tiene parámetros OUT o INOUT, callproc() devuelve una tupla que contiene los valores de estos parámetros después de que el procedimiento se haya ejecutado. El orden en esta tupla corresponde al orden de los parámetros OUT/INOUT en la lista de argumentos original.

6.5.2. Uso de Pool de Conexiones (introducción)

Abrir y cerrar una conexión a la base de datos para cada operación puede ser costoso en términos de rendimiento, especialmente en aplicaciones con muchas solicitudes concurrentes o frecuentes a la base de datos. El proceso de establecer una conexión implica una sobrecarga de red y autenticación.

Un pool de conexiones (connection pool) es una caché de conexiones a la base de datos que se mantienen abiertas y listas para ser reutilizadas por la aplicación. Cuando la aplicación necesita una conexión, la toma del pool; cuando termina, la devuelve al pool en lugar de cerrarla.

mysql-connector-python proporciona el módulo mysql.connector.pooling para implementar pools de conexiones.

Beneficios:

  • Mejora significativa del rendimiento al reducir la sobrecarga de creación de conexiones.
  • Gestión más eficiente de los recursos de conexión.
  • Control sobre el número máximo de conexiones al servidor.

Ejemplo Básico de Pool:

6.5.3. Separación de la lógica de base de datos del resto de la aplicación

Para mejorar la organización, mantenibilidad y testeabilidad de tu código, es una buena práctica separar la lógica de interacción con la base de datos del resto de la lógica de tu aplicación (lógica de negocio, interfaz de usuario, etc.).

Esto se puede lograr creando una capa de acceso a datos (Data Access Layer - DAL). Esta capa consistiría en módulos o clases Python cuyas responsabilidades son únicamente:

  • Establecer y gestionar conexiones a la base de datos (posiblemente usando un pool).
  • Definir funciones o métodos para cada operación CRUD específica que tu aplicación necesita (ej. get_estudiante_por_id(id), crear_nuevo_pedido(datos_pedido), etc.).
  • Encapsular las sentencias SQL y el manejo de cursores.
  • Manejar las excepciones de base de datos y, opcionalmente, traducirlas a excepciones más específicas de la aplicación.

Beneficios:

  • Código Más Limpio: La lógica de negocio no se mezcla con detalles de SQL.
  • Reusabilidad: Las funciones de acceso a datos se pueden reutilizar en diferentes partes de la aplicación.
  • Mantenibilidad: Si necesitas cambiar el SGBD o la forma en que se accede a los datos, los cambios se concentran en la DAL.
  • Testeabilidad: Es más fácil probar la lógica de negocio de forma aislada "moqueando" (simulando) la DAL.

6.6.1. ¿Qué es un ORM? Ventajas y Desventajas

Un ORM (Object-Relational Mapper - Mapeador Objeto-Relacional) es una técnica de programación y una herramienta (biblioteca o framework) que convierte datos entre sistemas de tipos incompatibles utilizando programación orientada a objetos. En el contexto de las bases de datos relacionales, un ORM permite a los desarrolladores interactuar con la base de datos utilizando objetos y clases de su lenguaje de programación (como Python) en lugar de escribir sentencias SQL directamente.

El ORM se encarga de "mapear" las clases de la aplicación a las tablas de la base de datos, las instancias de objetos a las filas, y los atributos de los objetos a las columnas.

Ventajas de usar un ORM:

  • Abstracción de la Base de Datos: Los desarrolladores pueden trabajar con objetos de Python en lugar de preocuparse por la sintaxis SQL específica o las diferencias entre SGBD (hasta cierto punto).
  • Productividad: Puede reducir la cantidad de código repetitivo (boilerplate) necesario para las operaciones CRUD.
  • Portabilidad (Potencial): Cambiar de un SGBD a otro puede ser más fácil si el ORM soporta ambos, ya que gran parte del código de la aplicación no necesitaría cambiar.
  • Modelo de Dominio Rico: Permite definir la lógica de negocio y las relaciones directamente en los modelos de objetos.
  • Características Adicionales: Muchos ORMs ofrecen funcionalidades como migraciones de esquema, validación de datos, gestión de relaciones complejas, etc.

Desventajas de usar un ORM:

  • Curva de Aprendizaje: Aprender a usar un ORM específico y sus particularidades puede llevar tiempo.
  • Abstracción con Fugas (Leaky Abstraction): A veces, para optimizar consultas complejas o usar características específicas del SGBD, es necesario "descender" al nivel de SQL o entender cómo el ORM traduce las operaciones a SQL.
  • Sobrecarga (Overhead): Los ORMs pueden introducir una capa de abstracción que añada algo de sobrecarga de rendimiento en comparación con SQL escrito a mano y optimizado.
  • Consultas Complejas: Expresar consultas muy complejas o específicas del SGBD puede ser difícil o menos intuitivo a través de la API del ORM.
  • "Magia": A veces, el ORM puede realizar muchas operaciones "bajo el capó", lo que puede dificultar la depuración o la comprensión exacta de lo que está sucediendo a nivel de base de datos.

La decisión de usar un ORM o escribir SQL directamente (o una combinación) depende del proyecto, la complejidad de las interacciones con la base de datos, la experiencia del equipo y las prioridades de rendimiento.

6.6.2. Breve introducción a SQLAlchemy

6.6.3. Breve introducción a Django ORM o Peewee

Existen otros ORMs populares en el ecosistema Python:

  • Django ORM:
    • Es el ORM integrado en el popular framework web Django.
    • Está fuertemente acoplado a la estructura y convenciones de Django.
    • Es conocido por su facilidad de uso (dentro de Django), su sistema de migraciones automático y su "admin" autogenerado.
    • Si estás desarrollando una aplicación web con Django, usar su ORM es la opción más natural.
    • La definición de modelos es similar a SQLAlchemy, pero con una sintaxis propia de Django.
  • Peewee ORM:
    • Es un ORM más pequeño, simple y expresivo.

    • Es una buena opción para proyectos más pequeños o medianos, o cuando se busca una alternativa ligera a SQLAlchemy.

    • La sintaxis para definir modelos y realizar consultas es bastante intuitiva.

-- 1. Crear la base de datos (si no existe)
CREATE DATABASE IF NOT EXISTS gestor_tareas_db

    COLLATE utf8mb4_unicode_ci;

-- 2. Seleccionar la base de datos
USE gestor_tareas_db;

-- 3. Crear la tabla 'tareas'
CREATE TABLE IF NOT EXISTS tareas (
    id INT AUTO_INCREMENT PRIMARY KEY,
    descripcion VARCHAR(255) NOT NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'pendiente' CHECK (estado IN ('pendiente', 'completada')),
    fecha_creacion TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    fecha_completado TIMESTAMP NULL DEFAULT NULL
);

-- 4. (Opcional) Describir la tabla para verificarla
-- DESCRIBE tareas;

Consideraciones sobre el diseño:

  • id: INT AUTO_INCREMENT PRIMARY KEY para un identificador único y automático.
  • descripcion: VARCHAR(255) NOT NULL asegura que siempre haya una descripción y limita su longitud.
  • estado: VARCHAR(20) NOT NULL DEFAULT 'pendiente'. Podríamos haber usado un ENUM('pendiente', 'completada'), pero VARCHAR con una restricción CHECK ofrece flexibilidad si quisiéramos añadir más estados después (aunque ALTER ENUM es posible, a veces es más engorroso). El DEFAULT 'pendiente' establece el estado inicial.
  • fecha_creacion: TIMESTAMP DEFAULT CURRENT_TIMESTAMP registra automáticamente cuándo se insertó la fila.
  • fecha_completado: TIMESTAMP NULL DEFAULT NULL permite que sea nulo inicialmente, y se actualizará cuando la tarea se complete.

def agregar_tarea(descripcion):
    """Agrega una nueva tarea a la base de datos."""
    conn = crear_conexion()
    if not conn or not conn.is_connected():
        return None # No se pudo conectar

    last_id = None
    try:
        with conn.cursor() as cursor:
            sql = "INSERT INTO tareas (descripcion) VALUES (%s)"
            cursor.execute(sql, (descripcion,))
            conn.commit()
            last_id = cursor.lastrowid
            print(f"Tarea '{descripcion}' agregada con ID: {last_id}.")
    except Error as e:
        print(f"Error al agregar tarea: {e}")
        if conn: conn.rollback()
    finally:
        if conn and conn.is_connected(): conn.close()
    return last_id

def obtener_tareas_pendientes():
    """Obtiene todas las tareas con estado 'pendiente'."""
    conn = crear_conexion()
    if not conn or not conn.is_connected():
        return []

    tareas_pendientes = []
    try:
        with conn.cursor(dictionary=True) as cursor:
            sql = "SELECT id, descripcion, DATE_FORMAT(fecha_creacion, '%Y-%m-%d %H:%i') AS fecha_c FROM tareas WHERE estado = 'pendiente' ORDER BY fecha_creacion ASC"
            cursor.execute(sql)
            tareas_pendientes = cursor.fetchall()
    except Error as e:
        print(f"Error al obtener tareas pendientes: {e}")
    finally:
        if conn and conn.is_connected(): conn.close()
    return tareas_pendientes

def marcar_tarea_completada(id_tarea):
    """Marca una tarea como 'completada' y establece la fecha de completado."""
    conn = crear_conexion()
    if not conn or not conn.is_connected():
        return False

    afectadas = 0
    try:
        with conn.cursor() as cursor:
            sql = "UPDATE tareas SET estado = 'completada', fecha_completado = CURRENT_TIMESTAMP WHERE id = %s AND estado = 'pendiente'"
            cursor.execute(sql, (id_tarea,))
            conn.commit()
            afectadas = cursor.rowcount
            if afectadas > 0:
                print(f"Tarea ID {id_tarea} marcada como completada.")
            else:
                print(f"Tarea ID {id_tarea} no encontrada o ya estaba completada.")
    except Error as e:
        print(f"Error al marcar tarea como completada: {e}")
        if conn: conn.rollback()
    finally:
        if conn and conn.is_connected(): conn.close()
    return afectadas > 0

def eliminar_tarea(id_tarea):
    """Elimina una tarea de la base de datos."""
    conn = crear_conexion()

        if conn: conn.rollback()
    finally:
        if conn and conn.is_connected(): conn.close()
    return afectadas > 0

def solicitar_id_tarea(accion="realizar una acción sobre"):
    while True:
        try:
